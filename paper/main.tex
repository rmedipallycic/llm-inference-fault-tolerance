\begin{abstract}
LLM inference servers stream generated tokens to clients over requests that
last seconds to minutes. When a serving process fails mid-generation, the
client is left holding a partial response, and the recovery it performs
determines what it ultimately shows a user or hands to a downstream agent.
We built an open-source fault-injection harness that SIGKILLs an unmodified
OpenAI-compatible server at a chosen token position, restarts it, applies a
client recovery strategy, and records every streamed chunk, and applied it
with identical code to vLLM and SGLang serving Llama~3.1~8B~Instruct on one
A10G GPU (60 trials per engine, plus a 20-trial cache ablation per engine).
In both engines' default configurations, the failure-free output for a fixed
prompt was not unique at temperature~0, for different reasons. In vLLM it
depended deterministically on what the server had served before, and
disabling automatic prefix caching removed the dependence. In SGLang the
second request on a running server was always the same, but the first
request after each start was not, and disabling the radix cache did not
change that. Because a crashed server restarts cold, naive retry, which
resubmits the prompt, contradicted text the client had already displayed in
25 of 30 vLLM trials and 24 of 30 SGLang trials. Recompute, which resubmits
the delivered text, never contradicted it, but its final text matched
neither failure-free output of its run in 24 of 30 and 26 of 30 trials.
Recovery latency was dominated by server restart (107--195\,s); the first
recovered token followed 0.23--0.51\,s after the server was ready. All raw
logs and the table-generating script are public.
\end{abstract}

\section{Introduction}

LLM serving has become stateful streaming infrastructure. A generation request
holds a growing key-value (KV) cache on an accelerator and emits tokens to the
client incrementally. Failure handling, however, is still largely stateless:
if the serving process dies, the client or a load balancer resubmits the
request and generation starts again.

That recovery has a cost that server-side metrics miss. A client that has
already displayed 128 tokens may receive those tokens a second time, may
receive a continuation that disagrees with what it already showed, or may lose
text at the boundary. For a chat interface this is a visible glitch. For an
agent that has already acted on a partial tool call or a partial plan, it is a
correctness problem. Stream processing systems name this property
\emph{delivery semantics} and engineer exactly-once output deliberately
\cite{elnozahy2002survey,carbone2015lightweight,armbrust2018structured}. LLM
serving has no equivalent definition, and to our knowledge no measurement of
what clients actually receive.

A common intuition is that at temperature 0 a retry is harmless: greedy
decoding is deterministic, so resubmitting the prompt reproduces the same
text and the client only has to drop the duplicate. Our measurements on vLLM
refute that intuition, and so do our measurements on SGLang, for a
different reason. In vLLM the output for a fixed prompt depended on what the
server had served earlier; in SGLang the first request after each server
start varied from start to start. Either way, the restarted server that
answers a retry does not reproduce the text the client was already shown.

This paper makes three contributions:
\begin{enumerate}
  \item \textbf{Definitions.} Token-level delivery semantics for streamed
    generation, and client-visible anomalies defined against \emph{two}
    failure-free references rather than one (Section~\ref{sec:model}).
  \item \textbf{A fault-injection harness} for any OpenAI-compatible server,
    which kills the full server process tree at a chosen chunk, restarts it,
    applies a client recovery strategy, and records every chunk with
    timestamps, the code commit, package versions, and GPU inventory
    (Section~\ref{sec:harness}).
  \item \textbf{A measurement study} of naive retry and recompute on vLLM
    and SGLang at temperature 0 and 0.8 and three kill positions, with a
    cache ablation for each engine
    (Sections~\ref{sec:method}--\ref{sec:results}), which finds that in
    both engines' default configurations failure-free output depends on
    server state, identifies the mechanism in vLLM, and quantifies what
    that does to each recovery strategy.
\end{enumerate}

The study deliberately uses unmodified engines and client-side recovery only.
It establishes the baseline that a server-side exactly-once protocol, the next
stage of this project, would have to improve on.

\section{Background}

\paragraph{Autoregressive serving.}
A request runs a prefill phase, which processes the prompt in parallel and
builds the KV cache, followed by a decode phase that produces one token per
step and streams it to the client. Engines such as vLLM \cite{kwon2023pagedattention}
and SGLang \cite{zheng2024sglang} batch requests at iteration granularity
\cite{yu2022orca} and manage the KV cache in fixed-size blocks.

\paragraph{The state lost on failure.}
The KV cache is a deterministic function of the weights and the token
sequence, so it can always be rebuilt by prefill. What cannot be rebuilt from
the prompt alone is the \emph{sampling path}: at temperature above zero, the
continuation depends on random draws whose state lives in the dead process.

\paragraph{Rollback-recovery vocabulary.}
Classic rollback-recovery distinguishes checkpointing from logging and defines
\emph{output commit}: a message to the outside world must not be released
until the state that produced it is recoverable \cite{elnozahy2002survey}.
Mapped onto LLM serving, the token sequence is a replayable input log, the KV
cache is derived operator state, and the streaming client is the external
sink where delivery semantics are decided.

\section{Delivery model and anomalies}
\label{sec:model}

A failure occurs after the client has received delivered text $D$. After
recovery the client receives recovery text $R$. What the client finally holds
depends on the strategy:
\textbf{naive retry} resubmits the original prompt with the original
\texttt{max\_tokens}, as many client retry wrappers do, and the retry is a
complete answer, so the final text is $F=R$;
\textbf{recompute} resubmits the prompt concatenated with $D$ and requests the
remaining token budget, so the server rebuilds the KV cache by prefill and
continues, and $F=D\cdot R$. Neither requires engine changes.

\paragraph{Two references.} Before the trials of each run, the harness
issues the request twice without failures and records both outputs: $G$, the
first request after the server starts, and $G'$, the second. A reproducible
server has $G=G'$. We do not assume this; we measure it, and compare every
final text with both.

\paragraph{Anomalies.}
\begin{itemize}
  \item \textbf{Contradiction} (naive retry): $R$ does not start with $D$,
    i.e.\ the replay disagrees with text the client has already displayed.
    A client that deduplicates by dropping the first $|D|$ characters of $R$
    would then splice two different texts. Recompute cannot contradict $D$
    by construction.
  \item \textbf{Duplication} (naive retry): the client receives $D$ again.
    Without contradiction this is full duplication, which an idempotent
    client can remove.
  \item \textbf{Divergence}: $F$ equals neither $G$ nor $G'$, i.e.\ the
    failure changed the final answer relative to any failure-free run we
    observed.
  \item \textbf{Recovery latency}: wall time from the kill to the first
    chunk delivered after recovery, which includes server restart.
\end{itemize}
Comparison is on text, not token ids, because the OpenAI-compatible streaming
API does not guarantee one token per chunk.

\section{Fault-injection harness}
\label{sec:harness}

The harness (\texttt{harness/}, about 340 lines of Python) has three parts.

\paragraph{Server lifecycle.} The server command is started in its own process
group and declared ready when \texttt{GET /v1/models} returns 200. A fault is a
\texttt{SIGKILL} of the whole process group, since vLLM and SGLang spawn worker
processes that otherwise keep holding GPU memory and the port. On Windows,
used only for laptop smoke tests, the equivalent is \texttt{taskkill /F /T}.

\paragraph{Streaming client.} Requests go to \texttt{/v1/completions} with
\texttt{stream=true}. Every server-sent event with non-empty text is recorded
as a chunk with wall-clock and monotonic timestamps. The kill fires from the
chunk callback when the configured chunk count is reached, and the client
keeps reading, so chunks the server had already sent before dying are recorded
as in-flight rather than lost.

\paragraph{Trial protocol.} Each run (one engine, strategy, temperature, and
kill position) starts the server, records two failure-free references $G$ and
$G'$, then for each trial: streams the request, kills at the kill point,
restarts the server and waits for readiness, issues the recovery request,
and writes a JSON record containing every chunk, the kill time, the restart
time, and the client view $V$.

\paragraph{Provenance.} Each run records the git commit and whether the
working tree was dirty, the full command line, installed versions of
\texttt{vllm}, \texttt{sglang}, \texttt{torch}, and \texttt{transformers}, the
GPU model, memory, and driver from \texttt{nvidia-smi}, and the full server
log. Measured runs are written to \texttt{experiments/} and committed; harness
smoke tests are written to a separate, git-ignored directory and are never
reported. Every table in this paper is generated by one script,
\texttt{analysis/make\_tables.py}, from those committed files.

\paragraph{Validation.} The harness was exercised end to end on a laptop CPU
with llama.cpp and a 0.5B model before any GPU run. That check, documented in
the repository as a mechanics check rather than a result, led to two changes:
a duplication metric based on shared prefix fraction rather than any shared
character, and the reference-reproducibility check, after two clean seeded
runs on that server disagreed at temperature 0.8.

\section{Methodology}
\label{sec:method}

\paragraph{Setup.} Two identical AWS \texttt{g5.xlarge} instances (one
NVIDIA A10G, 24\,GB; 4 vCPUs each; same machine image and driver), one per
engine, Llama~3.1~8B~Instruct in bf16. The harness code was identical for
both engines (commits \texttt{90da903} and \texttt{ddd8890} differ only
outside \texttt{harness/}).

\emph{vLLM} ran in its own Python 3.12
environment with default engine flags except a 4{,}096-token context cap
(Llama~3.1's 128k default does not fit a 24\,GB KV cache; every request here
is far shorter). Defaults include automatic prefix caching, which the server
logs confirm was on (\texttt{enable\_prefix\_caching=True}). The machine
image ships no CUDA toolkit, so FlashInfer's sampler, which compiles at
startup, was replaced by PyTorch sampling
(\texttt{VLLM\_USE\_FLASHINFER\_SAMPLER=0}); this is recorded in every run log.

\emph{SGLang} could not be started directly on that image, because several
of its components compile GPU code at startup (the attempts are documented
in the repository). It ran instead from the official container image
\texttt{lmsysorg/sglang:v0.5.21} (digest \texttt{sha256:b1259f3e\dots}),
which includes a CUDA 13.0 toolkit, with the harness running inside the same
container so that the process-group kill reaches the server. Flags were
defaults except the same 4{,}096-token context cap and
\texttt{--mem-fraction-static 0.85} (the default left no room for the KV
cache on 24\,GB). The server logs record what the defaults selected:
FlashInfer attention and sampling, CUDA graphs, radix cache on, and
deterministic inference off. The two engines therefore differ in kernels
and sampler as well as in design; we compare each engine's default
behaviour, not individual kernels. Versions are in Table~\ref{tab:env}.

\paragraph{Grid.} One fixed prompt (an explanation of write-ahead logging),
\texttt{max\_tokens}=256, per-request seed 1234. Strategy $\in$ \{naive
retry, recompute\} $\times$ temperature $\in \{0, 0.8\}$ $\times$ kill point
$\in$ \{25, 128, 230\} chunks (about 10\%, 50\%, and 90\% of the budget),
5 trials each: 12 runs and 60 trials per engine, produced by
\texttt{TRIALS=5 scripts/run\_matrix.sh vllm} and by
\texttt{scripts/sgl\_grid.sh} (the same grid with the SGLang flags above). Requests are issued one at a
time, so there is never more than one request in a batch.

\paragraph{Ablation.} After the vLLM grid showed $G\neq G'$, we repeated the
kill-at-128 configurations for both strategies and temperatures with
automatic prefix caching disabled (\texttt{--no-enable-prefix-caching}), all
else equal: 4 runs, 20 trials, labeled ``no APC''. For SGLang we ran the
same four configurations with its radix cache, the corresponding feature,
disabled (\texttt{--disable-radix-cache}), labeled ``no radix''.

\paragraph{Hypotheses.} Stated before the runs:
\begin{description}
  \item[H1] At temperature 0, naive retry yields full duplication in every
    trial and recompute yields $F=G$ in every trial.
  \item[H2] At temperature 0.8 with a fixed seed, vLLM reproduces $G$
    across clean runs; if so, naive retry still yields full duplication and
    recompute diverges after the kill point.
  \item[H3] Recovery latency is dominated by server restart, not by prefill
    of the delivered text.
\end{description}

\section{Results}
\label{sec:results}

\paragraph{vLLM: failure-free output was not unique.} In all 12 runs of the
default configuration, $G\neq G'$
(Table~\ref{tab:repro}). At temperature 0 the two references agreed for the
first 506 characters and then took different wording (``The log is scanned
from the end\dots'' versus ``The log is scanned to determine\dots''). With a
fixed seed at temperature 0.8 they diverged at character 9. Neither is noise:
every run's $G$ was identical to every other run's $G$ at the same
temperature, and likewise for $G'$. The output was a deterministic function
of the server's history, not of the prompt alone. Within a run, all trials
after the first produced identical text, so the 5 trials per configuration
are repeated observations of at most two distinct server histories, not
independent samples.

\paragraph{vLLM: naive retry contradicted the client.} The restarted server is
always in the state that produced $G$, and the replay equaled $G$ in all
30 naive-retry trials (Table~\ref{tab:anomalies}). The text the client had
already shown, $D$, came from a warm server and followed $G'$. Wherever the
kill fell after the point at which $G$ and $G'$ part, the replay therefore
contradicted $D$: in 25 of 30 trials, at character 506 at temperature 0 and
at character 9 at temperature 0.8. The only clean case was temperature 0
with the kill at 25 chunks (113 characters, before character 506), where the
replay began with $D$ and the anomaly was pure, removable duplication. A
client that drops the first $|D|$ characters of a replay, the usual
deduplication, would in the other 25 trials have produced a spliced text
that no failure-free run generated.

\paragraph{vLLM: recompute kept the shown text but changed the answer.} Recompute
never contradicted $D$, but its final text matched $G$ in 4 of 30 trials and
$G'$ in 2 of 30. At temperature 0 with the kill at 25 chunks, all five final
texts departed from both references at character 267, after the kill (113)
and before $G$ and $G'$ part (506): a third greedy output. The same third
point of departure appeared without any failure. In each recompute run, trials 1--4 ran on
a server whose only earlier request was trial~0's recovery (prompt plus $D$),
and their pre-kill streams, which no failure had yet touched, departed from
both references in 16 of 24 trials. The two $F{=}G'$ cases are trial~0 at
the 230-chunk kill; the four $F{=}G$ cases are trials 1--4 at temperature
0.8 with the kill at 25 chunks, where a 25-token recovery prefix left the
continuation on the cold-server path.

\paragraph{vLLM hypotheses.} \textbf{H1 is refuted}: at temperature 0, naive
retry gave full duplication only at the earliest kill point (5 of 15 trials)
and recompute never reproduced $G$ (0 of 15). \textbf{H2's premise is
refuted}: a fixed seed did not reproduce $G$ across requests, so its
predictions cannot be tested as stated. \textbf{H3 is supported}
(Table~\ref{tab:latency}): restart took 108--195\,s and the first recovered
token arrived 0.23--0.32\,s after the server was ready. Recompute's extra
prefill was visible but small: median time to first token after restart rose
from 0.24 to 0.27\,s at temperature 0 and from 0.28 to 0.31\,s at 0.8 as the
kill moved from 25 to 230 chunks, against 0.23--0.28\,s for naive retry.
The higher median restart for recompute is not a strategy effect: restart
happens before the recovery request is sent, and both initial startup and
restart rose from about 110--122\,s to 160--195\,s from the third trial of
the temperature-0, 230-chunk recompute run onward and stayed there for the
rest of the grid; the cause was not identified. In the ablation, run later
the same day, restarts were back to 107--120\,s.

\paragraph{vLLM prefix-cache ablation.} With automatic prefix caching disabled
(rows ``no APC''), $G=G'$ in all 4 runs at both temperatures
(Table~\ref{tab:repro}), and naive retry no longer contradicted the client:
in 10 of 10 trials the replay equaled both references and began with $D$, so
the anomaly was pure duplication that a client can remove
(Table~\ref{tab:anomalies}). The cache setting also changed the reference
itself at temperature 0: the no-APC output departs from the default
configuration's $G$ at character 267, although $G$ is the first request after
start, when the cache is empty. At temperature 0.8 the no-APC reference
equals the default $G$ exactly.

Recompute behaved differently by temperature. At 0.8 its final text equaled
$G$ in 5 of 5 trials. At temperature 0 it equaled neither reference in 5 of
5: all five departed at character 655, 43 characters after the kill (612), so
recompute changed the greedy answer even with no prefix cache. That final
text is character-for-character identical to the default configuration's
recompute text at the 25-chunk kill. Recompute's answer at temperature 0 is
therefore not explained by the cache. It is consistent with the delivered
text being processed as prompt (prefill) rather than generated (decode), or
with re-tokenization of $D$; these data do not separate the two.

\paragraph{SGLang: the first request after a start was not reproducible.}
SGLang showed a different pattern (Table~\ref{tab:repro}). At temperature 0
the second request on a running server, $G'$, was the same text in all 6
runs, but the first request after a start was not: the 21
first-after-start outputs we recorded (6 references $G$ and 15 naive-retry
replays) contained 10 distinct texts, none equal to $G'$, departing from it
at characters 267 to 676. Disabling the radix cache did not change this:
$G'$ was again the same in both runs, and 7 first-after-start outputs gave 4
distinct texts. In SGLang the output therefore depended on whether the server
had just started, not on cache contents, and the cold output was not
repeatable from one start to the next. We did not identify the source. One
untested candidate is that, with no seed given, SGLang chooses a new server
random seed at every start; the logs record a different value each time.

At temperature 0.8 the request seed had no observable effect: $G$ and $G'$
diverged within the first two characters in all 8 runs, and the 20
naive-retry pre-kill streams were all different. SGLang provides seeded,
reproducible sampling through an opt-in deterministic mode with a seed in
its own sampling parameters \cite{sglang2025deterministic}; our harness sends
the OpenAI-style \texttt{seed} and did not enable that mode, so SGLang's 0.8
results describe unseeded sampling.

\paragraph{SGLang: the same consequences.} Naive retry contradicted text
already shown in 24 of 30 default-configuration trials: at temperature 0 in
0, 4 and 5 of 5 trials as the kill moved from 25 to 128 to 230 chunks
(the warm stream $D$ followed $G'$, the cold replay did not), and at 0.8 in
15 of 15. Without the radix cache it did so in 10 of 10. Recompute never
contradicted $D$, and its final text matched neither failure-free output of
its run in 26 of 30 default-configuration trials. Recovery was again
dominated by restart (Table~\ref{tab:latency}): 125--145\,s with the radix
cache on, and the first recovered token 0.33--0.51\,s after the server was
ready. Restarts in the no-radix runs, which ran last, took 172--195\,s; as
with vLLM's drift, we did not identify the cause and do not attribute it to
the cache setting.
For SGLang, as for vLLM, \textbf{H1 is refuted} (at temperature 0 naive
retry gave full duplication only at the earliest kill point, and recompute
reproduced $G$ in 3 of 15 trials), \textbf{H2's premise is refuted} (the
seed had no observable effect), and \textbf{H3 is supported}.

\section{Discussion}

\paragraph{Two engines, two mechanisms, one consequence.} vLLM's variation
was deterministic and tied to its prefix cache; SGLang's was tied to server
start and was not repeatable across starts. A client cannot tell these
apart, and for a client they have the same effect: the server that answers
a retry is freshly started, and a freshly started server did not reproduce
the text the client had been shown, in 25 of 30 vLLM and 24 of 30 SGLang
trials.

\paragraph{Retry is not replay.} The usual argument for retrying an LLM
request is that at temperature 0 it is idempotent up to duplication. On the
default vLLM configuration measured here, it was not: the server that
answers a retry is a fresh process, and a fresh process gave a different
greedy answer from the warm one that had been streaming. For a chat client
this means a visible rewrite of text already shown in most trials on both
engines; for an
agent that acted on a partial tool call or plan, it means the action was
based on text that the final answer contradicts.

\paragraph{What a client should do.} Within these measurements, on both
engines, recompute is the only client-side strategy that never contradicted
what was shown, at the
price of a final answer that no failure-free run produced, and a few tens of
milliseconds of extra prefill. Naive retry with deduplication is unsafe
unless the client verifies that the replay begins with $D$, and should
replace rather than splice when it does not. On vLLM, an operator can
remove the contradictions by disabling automatic prefix caching, as the
ablation did; we did not measure the throughput cost, which on workloads
with shared prefixes is the reason the cache exists. On SGLang, disabling
the radix cache did not help; its opt-in deterministic mode
\cite{sglang2025deterministic} is the natural next configuration to test.

\paragraph{Why client-side recovery is not enough.} Even in the best case for
recompute, the client cannot restore the server's state: neither the
sampler's random state above temperature 0 nor, as measured here, whatever
server state made $G$ differ from $G'$; and even with that state removed
by disabling the prefix cache, recompute at temperature 0 did not reproduce
the original continuation. Exactly-once delivery therefore
requires state the client does not hold: a sequence-numbered token log, and
the sampler state, committed before tokens are released, with recovery
continuing from the log rather than regenerating. That protocol is the next
stage of this project, and these measurements are its baseline.

\section{Related work}

\textbf{Fault-tolerant LLM serving.} D\'ej\`aVu \cite{strati2024dejavu}
streams and replicates KV cache to recover from failures and reports
server-side recovery time; it does not characterize what streaming clients
receive. SpotServe \cite{miao2024spotserve} migrates in-flight context when
preemptible instances are reclaimed with warning, and Llumnix
\cite{sun2024llumnix} live-migrates requests for load balancing. Both handle
planned moves; this study targets unplanned fail-stop crashes.
\textbf{Serving engines.} Orca \cite{yu2022orca} introduced iteration-level
scheduling, vLLM \cite{kwon2023pagedattention} block-managed KV memory, and
SGLang \cite{zheng2024sglang} prefix sharing via RadixAttention.
\textbf{Delivery semantics.} Chandy and Lamport \cite{chandy1985snapshots}
define consistent snapshots, Elnozahy et al.\ \cite{elnozahy2002survey}
output commit, and Flink \cite{carbone2015lightweight} and Spark Structured
Streaming \cite{armbrust2018structured} build exactly-once sinks on them.
\textbf{Inference nondeterminism.} He et al.\ \cite{he2025nondeterminism}
show that LLM inference at temperature 0 is not reproducible across server
load because kernels are not batch-invariant, and build batch-invariant
kernels. Our observation is the fault-tolerance consequence: requests here
were issued one at a time, yet output still depended on what the server had
served before, so a retry after a crash is not a replay.
Optimal checkpoint intervals \cite{young1974first,daly2006higher} motivate
later stages of this project.

\section{Threats to validity}

\begin{itemize}
  \item \textbf{Trials are not independent samples.} In vLLM, output was
    deterministic given server history, so 5 trials per configuration are
    repeated observations of one or two histories, and counts such as ``25
    of 30'' describe how many configurations and histories were affected,
    not a sampled rate. In SGLang the cold output varied from start to
    start, so its trials do sample that variation, but 5 per configuration
    is too few to estimate rates.
  \item \textbf{One prompt, one model, one GPU.} The divergence positions
    (characters 506 and 9) are specific to this prompt and to Llama~3.1~8B
    on an A10G. Other prompts may diverge earlier, later, or not at all
    within 256 tokens; tensor-parallel serving may differ.
  \item \textbf{Default configurations, different kernels.} Each engine
    ran with its own defaults on this GPU (vLLM with PyTorch sampling
    because FlashInfer's sampler could not compile on the host image;
    SGLang with FlashInfer attention and sampling inside its container).
    The comparison is between default behaviours, not kernels.
  \item \textbf{SGLang seed.} The harness's OpenAI-style seed had no
    observable effect on SGLang, so its temperature-0.8 results are for
    unseeded sampling and are not comparable to vLLM's seeded runs.
    Its temperature-0 results do not involve sampling.
  \item \textbf{vLLM sampler substitution.} vLLM ran with PyTorch sampling
    instead of FlashInfer's sampler, because of the missing CUDA toolkit. The
    temperature-0 results do not involve random sampling, but the 0.8
    results may differ under FlashInfer.
  \item \textbf{Mechanism.} For vLLM, the ablation shows that, on this
    setup, the dependence on server history requires automatic prefix
    caching. For SGLang, the radix cache was not required, and the source of
    the start-to-start variation was not identified. It does
    not show which computation inside the cached path differs; kernels whose
    results depend on batch or prefill shape \cite{he2025nondeterminism} are
    a plausible candidate that we did not test. The ablation covered only
    the 128-chunk kill point (20 trials per engine).
  \item \textbf{Re-tokenization in recompute.} Recompute sends $D$ as text,
    which the engine re-tokenizes; a boundary that tokenizes differently can
    change the continuation. The recompute departures observed here were
    after the kill boundary (e.g.\ character 267 against a kill at 113).
  \item \textbf{Fail-stop only; latency includes restart.} \texttt{SIGKILL}
    is a clean crash; GPU hangs and silent corruption are not modeled. With
    a single instance, recovery includes model reload; a warm standby would
    be faster. Restart time also drifted during the grid (see H3).
\end{itemize}

\section{Conclusion and future work}

In the default configurations of both vLLM and SGLang, the failure-free
output for a fixed prompt was not unique at temperature 0: in vLLM it
depended on what the server had served before, through automatic prefix
caching; in SGLang the first request after each start varied, with or
without its radix cache. As a result, naive retry after a crash contradicted
text the client had already shown in 25 of 30 vLLM and 24 of 30 SGLang
trials, and recompute, while never contradicting it, produced a final text
matching neither failure-free output of its run in most trials on both
engines. A retry after a crash is not a replay, and exactly-once delivery
needs state the client does not have.

Next stages: (0) more prompts and models, and both engines' deterministic
or batch-invariant modes \cite{he2025nondeterminism,sglang2025deterministic}; (1) a gateway that assigns sequence numbers,
logs tokens and sampler state before release, and continues from the log on
recovery, evaluated on the same harness for zero anomalies and per-token
overhead; (2) measured recompute-versus-checkpoint cost curves for the KV
cache; (3) an adaptive per-request checkpoint policy.
