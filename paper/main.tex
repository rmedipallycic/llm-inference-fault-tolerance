\begin{abstract}
LLM inference servers stream tokens to clients over requests lasting seconds
to minutes; when a serving process fails mid-generation, the recovery decides
what the client finally shows a user or hands to an agent. With an
open-source fault-injection harness that SIGKILLs unmodified vLLM and SGLang
servers (Llama~3.1~8B, A10G GPUs), we report three results. First, retry is
not replay: in both engines' default configurations the failure-free output
was not unique at temperature~0, so naive retry contradicted text already
shown in 25 of 30 vLLM and 24 of 30 SGLang trials; each engine's
deterministic mode with recompute made recovery exact, at
\TputDetMin--\TputDetMax$\times$ the default throughput under load. Second,
a gateway that numbers output positions, logs them before release and
resumes from the logged token ids delivered every output position (a token
on vLLM, a stream chunk on SGLang) exactly once, under stated assumptions, in all \GwKillTrials{} single-request failures
and all \PccRecords{} requests of failures with 4--32 requests in flight. The
text a client displays is a separate property: vLLM repeated earlier text
after a resume \RevRepeatRemoved{} times, which the gateway removed, and the
client's text was correct in \RevTextOk{} of \RevRecords{} requests. The three
exceptions, first tokens of prompts sent as token ids, were fixed afterwards;
a targeted check on vLLM with \TbPrompts{} such prompts found the fixed
gateway's text correct in all of them, with 1 and 16 requests in flight.
Third, recovery time
depends on where state is kept: a standby replica cut recovery from minutes
to \GwFailoverMin--\GwFailoverMax\,s for a short prompt, and vLLM's own KV
offloading to storage the standby reads cut it from \PfbSixteenNone\,s to
\PfbSixteenPrompt\,s at 16K prompt tokens, and from a median of
\PccThirtyTwoNone\,s to \PccThirtyTwoPrompt\,s with 32 requests in flight, for
under 1\% decoding cost and 5--8\% later first tokens. A simulation driven by
the measurements found no benefit from adaptive checkpoint policies. All raw
logs and table-generating scripts are public.
\end{abstract}

\section{Introduction}

LLM serving has become stateful streaming infrastructure. A generation request
holds a growing key-value (KV) cache on an accelerator and emits tokens to the
client incrementally. Failure handling, however, is still largely stateless:
if the serving process dies, the client or a load balancer resubmits the
request and generation starts again.

That recovery has a cost that server-side metrics miss. A client that has
already displayed 128 tokens may receive those tokens a second time, may
receive a continuation that disagrees with what it already showed, or may lose
text at the boundary. For a chat interface this is a visible glitch. For an
agent that has already acted on a partial tool call or a partial plan, it is a
correctness problem. Stream processing systems name this property
\emph{delivery semantics} and engineer exactly-once output deliberately
\cite{elnozahy2002survey,carbone2015lightweight,armbrust2018structured}. LLM
serving has no equivalent definition, and to our knowledge no measurement of
what clients actually receive.

A common intuition is that at temperature 0 a retry is harmless: greedy
decoding is deterministic, so resubmitting the prompt reproduces the same
text and the client only has to drop the duplicate. Our measurements on vLLM
refute that intuition, and so do our measurements on SGLang, for a
different reason. In vLLM the output for a fixed prompt depended on what the
server had served earlier; in SGLang the first request after each server
start varied from start to start. Either way, the restarted server that
answers a retry does not reproduce the text the client was already shown.

This paper makes four contributions:
\begin{enumerate}
  \item \textbf{Client-visible anomalies, defined and measured.} Token-level
    delivery semantics for streamed generation, with anomalies defined
    against \emph{two} failure-free references (Section~\ref{sec:model}); a
    fault-injection harness for any OpenAI-compatible server
    (Section~\ref{sec:harness}); and a study of naive retry and recompute on
    vLLM and SGLang with cache ablations, deterministic modes and six prompts
    (Sections~\ref{sec:method}--\ref{sec:followup}), which finds that in both
    engines' default configurations failure-free output depends on server
    state, so naive retry contradicts text already shown.
  \item \textbf{A gateway protocol} in front of unmodified engines that
    numbers and logs output positions before releasing them and resumes a
    failed request from the logged token ids, with its guarantee stated
    precisely: what it covers (positions; text derived from token ids), and
    what it assumes (fail-stop crashes, a surviving log, a client that
    remembers its position) (Section~\ref{sec:gateway}).
  \item \textbf{Recovery and determinism, evaluated.} 190 injected failures
    through the gateway on both engines, including failover between two
    machines, where exact text needed matching compiled state in our runs
    (Section~\ref{sec:gweval}); the cost of the deterministic modes under
    concurrent load (Section~\ref{sec:load}); and failures with up to 32
    requests in flight (Section~\ref{sec:live}).
  \item \textbf{KV-checkpoint analysis.} Measured recompute and KV-copy costs
    from 512 to 32{,}768 tokens (Section~\ref{sec:restore}); a simulation of
    checkpoint policies judged by a decision rule written before it ran
    (Section~\ref{sec:sim}); and vLLM's built-in KV offloading used as a live
    checkpoint, measured while serving and through failover
    (Section~\ref{sec:live}).
\end{enumerate}

The first part of the study (Sections~\ref{sec:method}--\ref{sec:followup})
deliberately uses unmodified engines and client-side recovery only, and
establishes the baseline. The second part
(Sections~\ref{sec:gateway}--\ref{sec:gweval}) asks what a server-side
protocol in front of the same engines achieves against it. The third part
(Sections~\ref{sec:load}--\ref{sec:live}) measures what the fixes and the
gateway cost under load and how much a KV-cache checkpoint shortens
recovery. This is version 3 of the paper; version 1 contained the first part,
version 2 added the second.

\section{Background}

\paragraph{Autoregressive serving.}
A request runs a prefill phase, which processes the prompt in parallel and
builds the KV cache, followed by a decode phase that produces one token per
step and streams it to the client. Engines such as vLLM \cite{kwon2023pagedattention}
and SGLang \cite{zheng2024sglang} batch requests at iteration granularity
\cite{yu2022orca} and manage the KV cache in fixed-size blocks.

\paragraph{The state lost on failure.}
The KV cache is a deterministic function of the weights and the token
sequence, so it can always be rebuilt by prefill, up to numerical
differences between prefill and decode kernels. At temperature above zero
the continuation also depends on random draws. Whether those can be
reproduced after a restart depends on the engine: a sampler that keeps a
running random state loses it with the process, while one that derives each
draw from the request's seed and the token's position, as vLLM~0.31 does
(Section~\ref{sec:gweval}), can repeat it.

\paragraph{Rollback-recovery vocabulary.}
Classic rollback-recovery distinguishes checkpointing from logging and defines
\emph{output commit}: a message to the outside world must not be released
until the state that produced it is recoverable \cite{elnozahy2002survey}.
Mapped onto LLM serving, the token sequence is a replayable input log, the KV
cache is derived operator state, and the streaming client is the external
sink where delivery semantics are decided.

\section{Delivery model and anomalies}
\label{sec:model}

A failure occurs after the client has received delivered text $D$. After
recovery the client receives recovery text $R$. What the client finally holds
depends on the strategy:
\textbf{naive retry} resubmits the original prompt with the original
\texttt{max\_tokens}, as many client retry wrappers do, and the retry is a
complete answer, so the final text is $F=R$;
\textbf{recompute} resubmits the prompt concatenated with $D$ and requests the
remaining token budget, so the server rebuilds the KV cache by prefill and
continues, and $F=D\cdot R$. Neither requires engine changes. When the
failure occurs, $D$ has already been shown to a user or passed to a
consumer. $F=R$ for naive retry assumes the client replaces what it
showed; a client that instead appends the replay after dropping its first
$|D|$ characters is the case the contradiction metric below captures.

\paragraph{Two references.} Before the trials of each run, the harness
issues the request twice without failures and records both outputs: $G$, the
first request after the server starts, and $G'$, the second. A reproducible
server has $G=G'$. We do not assume this; we measure it, and compare every
final text with both.

\paragraph{Anomalies.}
\begin{itemize}
  \item \textbf{Contradiction} (naive retry): $R$ does not start with $D$,
    i.e.\ the replay disagrees with text the client has already displayed.
    A client that deduplicates by dropping the first $|D|$ characters of $R$
    would then splice two different texts. Recompute cannot contradict $D$
    by construction.
  \item \textbf{Duplication} (naive retry): the client receives $D$ again.
    Without contradiction this is full duplication, which an idempotent
    client can remove.
  \item \textbf{Divergence}: $F$ equals neither $G$ nor $G'$, i.e.\ the
    failure changed the final answer relative to any failure-free run we
    observed.
  \item \textbf{Recovery latency}: wall time from the kill to the first
    chunk delivered after recovery, which includes server restart.
\end{itemize}
Comparison is on text, not token ids, because the OpenAI-compatible streaming
API does not guarantee one token per chunk.

\section{Fault-injection harness}
\label{sec:harness}

The harness (\texttt{harness/}, about 340 lines of Python) has three parts.

\paragraph{Server lifecycle.} The server command is started in its own process
group and declared ready when \texttt{GET /v1/models} returns 200. A fault is a
\texttt{SIGKILL} of the whole process group, since vLLM and SGLang spawn worker
processes that otherwise keep holding GPU memory and the port. On Windows,
used only for laptop smoke tests, the equivalent is \texttt{taskkill /F /T}.

\paragraph{Streaming client.} Requests go to \texttt{/v1/completions} with
\texttt{stream=true}. Every server-sent event with non-empty text is recorded
as a chunk with wall-clock and monotonic timestamps. The kill fires from the
chunk callback when the configured chunk count is reached, and the client
keeps reading, so chunks the server had already sent before dying are recorded
as in-flight rather than lost. Kill points are counted in chunks, not tokens. In
the 10 vLLM trials that recorded token ids, every chunk before the kill
carried exactly one token, so there the two coincide; after recovery, one
chunk per trial carried 9 or 10 tokens.

\paragraph{Trial protocol.} Each run (one engine, strategy, temperature, and
kill position) starts the server, records two failure-free references $G$ and
$G'$, then for each trial: streams the request, kills at the kill point,
restarts the server and waits for readiness, issues the recovery request,
and writes a JSON record containing every chunk, the kill time, the restart
time, and the client view $V$.

\paragraph{Provenance.} Each run records the git commit and whether the
working tree was dirty, the full command line, installed versions of
\texttt{vllm}, \texttt{sglang}, \texttt{torch}, and \texttt{transformers}, the
GPU model, memory, and driver from \texttt{nvidia-smi}, and the full server
log. Measured runs are written to \texttt{experiments/} and committed; harness
smoke tests are written to a separate, git-ignored directory and are never
reported. Every table in this paper is generated by one script,
\texttt{analysis/make\_tables.py}, from those committed files.

\paragraph{Validation.} The harness was exercised end to end on a laptop CPU
with llama.cpp and a 0.5B model before any GPU run. That check, documented in
the repository as a mechanics check rather than a result, led to two changes:
a duplication metric based on shared prefix fraction rather than any shared
character, and the reference-reproducibility check, after two clean seeded
runs on that server disagreed at temperature 0.8.

\section{Methodology}
\label{sec:method}

\paragraph{Setup.} Two identical AWS \texttt{g5.xlarge} instances (one
NVIDIA A10G, 24\,GB; 4 vCPUs each; same machine image and driver), one per
engine, Llama~3.1~8B~Instruct in bf16. The harness code was identical for
both engines (commits \texttt{90da903} and \texttt{ddd8890} differ only
outside \texttt{harness/}).

\emph{vLLM} ran in its own Python 3.12
environment with default engine flags except a 4{,}096-token context cap
(Llama~3.1's 128k default does not fit a 24\,GB KV cache; every request here
is far shorter). Defaults include automatic prefix caching, which the server
logs confirm was on (\texttt{enable\_prefix\_caching=True}). The machine
image ships no CUDA toolkit, so FlashInfer's sampler, which compiles at
startup, was replaced by PyTorch sampling
(\texttt{VLLM\_USE\_FLASHINFER\_SAMPLER=0}); this is recorded in every run log.

\emph{SGLang} could not be started directly on that image, because several
of its components compile GPU code at startup (the attempts are documented
in the repository). It ran instead from the official container image
\texttt{lmsysorg/sglang:v0.5.21} (digest \texttt{sha256:b1259f3e\dots}),
which includes a CUDA 13.0 toolkit, with the harness running inside the same
container so that the process-group kill reaches the server. Flags were
defaults except the same 4{,}096-token context cap and
\texttt{--mem-fraction-static 0.85} (the default left no room for the KV
cache on 24\,GB). The server logs record what the defaults selected:
FlashInfer attention and sampling, CUDA graphs, radix cache on, and
deterministic inference off. The two engines therefore differ in kernels
and sampler as well as in design; we compare each engine's default
behaviour, not individual kernels. Versions are in Table~\ref{tab:env}.

\paragraph{Grid.} One fixed prompt (an explanation of write-ahead logging),
\texttt{max\_tokens}=256, per-request seed 1234. Strategy $\in$ \{naive
retry, recompute\} $\times$ temperature $\in \{0, 0.8\}$ $\times$ kill point

5 trials each: 12 runs and 60 trials per engine, produced by
\texttt{TRIALS=5 scripts/run\_matrix.sh vllm} and by
\texttt{scripts/sgl\_grid.sh} (the same grid with the SGLang flags above). Requests are issued one at a
time, so there is never more than one request in a batch.

\paragraph{Ablation.} After the vLLM grid showed $G\neq G'$, we repeated the
kill-at-128 configurations for both strategies and temperatures with
automatic prefix caching disabled (\texttt{--no-enable-prefix-caching}), all
else equal: 4 runs, 20 trials, labeled ``no APC''. For SGLang we ran the
same four configurations with its radix cache, the corresponding feature,
disabled (\texttt{--disable-radix-cache}), labeled ``no radix''.

\paragraph{Follow-up runs.} After the first results, a second set of runs
(harness commit \texttt{9510da0}, scripts \texttt{scripts/extras\_*.sh}),
all at the 128-chunk kill point with 5 trials each, tested the open
questions: (i) each engine's deterministic mode, vLLM's batch invariance
(\texttt{VLLM\_BATCH\_INVARIANT=1}) and SGLang's deterministic inference
(\texttt{--enable-deterministic-inference}, with \texttt{sampling\_seed}
1234 in each request), on the original prompt at both temperatures;
(ii) SGLang with a fixed server seed (\texttt{--random-seed 1234});
(iii) a vLLM recompute variant, \emph{recompute (ids)}, that resubmits token
ids (the prompt's ids from \texttt{/tokenize} plus the delivered tokens'
ids) instead of text, and records whether re-tokenizing the delivered text
would have produced the same ids; and (iv) five further prompts (a TCP
explanation, a short story, a coffee recipe, processes versus threads, and
the 2008 financial crisis; \texttt{harness/prompts.json}) at temperature 0,
for each engine in its default and its fixed configuration (vLLM without
prefix caching, SGLang deterministic). That is 54 runs and 270 trials.

\paragraph{Hypotheses.} Stated before the runs:
\begin{description}
  \item[H1] At temperature 0, naive retry yields full duplication in every
    trial and recompute yields $F=G$ in every trial.
  \item[H2] At temperature 0.8 with a fixed seed, vLLM reproduces $G$
    across clean runs; if so, naive retry still yields full duplication and
    recompute diverges after the kill point.
  \item[H3] Recovery latency is dominated by server restart, not by prefill
    of the delivered text.
\end{description}

\section{Results}
\label{sec:results}

\paragraph{vLLM: failure-free output was not unique.} In all 12 runs of the
default configuration, $G\neq G'$
(Table~\ref{tab:repro}). At temperature 0 the two references agreed for the
first 506 characters and then took different wording (``The log is scanned
from the end\dots'' versus ``The log is scanned to determine\dots''). With a
fixed seed at temperature 0.8 they diverged at character 9. Neither is noise:
every run's $G$ was identical to every other run's $G$ at the same
temperature, and likewise for $G'$. The output was a deterministic function
of the server's history, not of the prompt alone. Within a run, all trials
after the first produced identical text, so the 5 trials per configuration
are repeated observations of at most two distinct server histories, not
independent samples.

\paragraph{vLLM: naive retry contradicted the client.} Counts such as
``25 of 30'' below are observed trial outcomes, not estimates of how often
this happens in production (Section~\ref{sec:threats}). The restarted server is
always in the state that produced $G$, and the replay equaled $G$ in all
30 naive-retry trials (Table~\ref{tab:anomalies}). The text the client had
already shown, $D$, came from a warm server and followed $G'$. Wherever the
kill fell after the point at which $G$ and $G'$ part, the replay therefore
contradicted $D$: in 25 of 30 trials, at character 506 at temperature 0 and
at character 9 at temperature 0.8. The only clean case was temperature 0
with the kill at 25 chunks (113 characters, before character 506), where the
replay began with $D$ and the anomaly was pure, removable duplication. A
client that drops the first $|D|$ characters of a replay, the usual
deduplication, would in the other 25 trials have produced a spliced text
that no failure-free run generated.

\paragraph{vLLM: recompute kept the shown text but changed the answer.} Recompute
never contradicted $D$, but its final text matched $G$ in 4 of 30 trials and
$G'$ in 2 of 30. At temperature 0 with the kill at 25 chunks, all five final
texts departed from both references at character 267, after the kill (113)
and before $G$ and $G'$ part (506): a third greedy output. The same third
point of departure appeared without any failure. In each recompute run, trials 1--4 ran on
a server whose only earlier request was trial~0's recovery (prompt plus $D$),
and their pre-kill streams, which no failure had yet touched, departed from
both references in 16 of 24 trials. The two $F{=}G'$ cases are trial~0 at
the 230-chunk kill; the four $F{=}G$ cases are trials 1--4 at temperature
0.8 with the kill at 25 chunks, where a 25-token recovery prefix left the
continuation on the cold-server path.

\paragraph{vLLM hypotheses.} \textbf{H1 is refuted}: at temperature 0, naive
retry gave full duplication only at the earliest kill point (5 of 15 trials)
and recompute never reproduced $G$ (0 of 15). \textbf{H2's premise is
refuted}: a fixed seed did not reproduce $G$ across requests, so its
predictions cannot be tested as stated. \textbf{H3 is supported}
(Table~\ref{tab:latency}): restart took 108--195\,s and the first recovered
token arrived 0.23--0.32\,s after the server was ready. Recompute's extra
prefill was visible but small: median time to first token after restart rose
from 0.24 to 0.27\,s at temperature 0 and from 0.28 to 0.31\,s at 0.8 as the
kill moved from 25 to 230 chunks, against 0.23--0.28\,s for naive retry.
The higher median restart for recompute is not a strategy effect: restart
happens before the recovery request is sent, and both initial startup and
restart rose from about 110--122\,s to 160--195\,s from the third trial of
the temperature-0, 230-chunk recompute run onward and stayed there for the
rest of the grid; the cause was not identified. In the ablation, run later
the same day, restarts were back to 107--120\,s.

\paragraph{vLLM prefix-cache ablation.} With automatic prefix caching disabled
(rows ``no APC''), $G=G'$ in all 4 runs at both temperatures
(Table~\ref{tab:repro}), and naive retry no longer contradicted the client:
in 10 of 10 trials the replay equaled both references and began with $D$, so
the anomaly was pure duplication that a client can remove
(Table~\ref{tab:anomalies}). The cache setting also changed the reference
itself at temperature 0: the no-APC output departs from the default
configuration's $G$ at character 267, although $G$ is the first request after
start, when the cache is empty. At temperature 0.8 the no-APC reference
equals the default $G$ exactly.

Recompute behaved differently by temperature. At 0.8 its final text equaled
$G$ in 5 of 5 trials. At temperature 0 it equaled neither reference in 5 of
5: all five departed at character 655, 43 characters after the kill (612), so
recompute changed the greedy answer even with no prefix cache. That final
text is character-for-character identical to the default configuration's
recompute text at the 25-chunk kill. Recompute's answer at temperature 0 is
therefore not explained by the cache. It is consistent with the delivered
text being processed as prompt (prefill) rather than generated (decode), or
with re-tokenization of $D$; these data do not separate the two.

\paragraph{SGLang: the first request after a start was not reproducible.}
SGLang showed a different pattern (Table~\ref{tab:repro}). At temperature 0
the second request on a running server, $G'$, was the same text in all 6
runs, but the first request after a start was not: the 21
first-after-start outputs we recorded (6 references $G$ and 15 naive-retry
replays) contained 10 distinct texts, none equal to $G'$, departing from it
at characters 267 to 676. Disabling the radix cache did not change this:
$G'$ was again the same in both runs, and 7 first-after-start outputs gave 4
distinct texts. In SGLang the output therefore depended on whether the server
had just started, not on cache contents, and the cold output was not
repeatable from one start to the next. We did not identify the source. One
untested candidate is that, with no seed given, SGLang chooses a new server
random seed at every start; the logs record a different value each time.

At temperature 0.8 the request seed had no observable effect: $G$ and $G'$
diverged within the first two characters in all 8 runs, and the 20
naive-retry pre-kill streams were all different. SGLang provides seeded,
reproducible sampling through an opt-in deterministic mode with a seed in
its own sampling parameters \cite{sglang2025deterministic}; our harness sends
the OpenAI-style \texttt{seed} and did not enable that mode, so SGLang's 0.8
results describe unseeded sampling.

\paragraph{SGLang: the same consequences.} Naive retry contradicted text
already shown in 24 of 30 default-configuration trials: at temperature 0 in
0, 4 and 5 of 5 trials as the kill moved from 25 to 128 to 230 chunks
(the warm stream $D$ followed $G'$, the cold replay did not), and at 0.8 in
15 of 15. Without the radix cache it did so in 10 of 10. Recompute never
contradicted $D$, and its final text matched neither failure-free output of
its run in 26 of 30 default-configuration trials. Recovery was again
dominated by restart (Table~\ref{tab:latency}): 125--145\,s with the radix
cache on, and the first recovered token 0.33--0.51\,s after the server was
ready. Restarts in the no-radix runs, which ran last, took 172--195\,s; as
with vLLM's drift, we did not identify the cause and do not attribute it to
the cache setting.
For SGLang, as for vLLM, \textbf{H1 is refuted} (at temperature 0 naive
retry gave full duplication only at the earliest kill point, and recompute
reproduced $G$ in 3 of 15 trials), \textbf{H2's premise is refuted} (the
seed had no observable effect), and \textbf{H3 is supported}.

\section{An exactly-once gateway}
\label{sec:gateway}

The measurements above leave recovery to the client, which then has to
resubmit, splice and deduplicate. The gateway (\texttt{gateway/}, about 650
lines of Python with no dependencies beyond \texttt{requests}) moves that work
to a process in front of unmodified engine replicas. An ordinary streaming
client works unchanged: it uses the usual OpenAI-compatible API and needs no
recovery code for engine failures, which the gateway handles. Only for the
client's own connection to the gateway, or a gateway restart, does the
end-to-end guarantee below ask more of the client: remembering the last
position it consumed and reconnecting from there.

\paragraph{Protocol.} (1) \emph{Numbering}: every streamed entry carries
\texttt{seq}, the position of its first output token, and \texttt{n}, the
number of tokens it holds, in an extra field of the server-sent event.
(2) \emph{Output commit}: each entry is appended to a per-request log file,
optionally with \texttt{fsync}, before it is released to the client
\cite{elnozahy2002survey}, so the log contains everything the client has
seen. (3) \emph{Engine failure}: a broken stream, an HTTP error, or no chunk
for a stall timeout counts as a failed attempt. The gateway picks a healthy
replica, trying the others before the one that failed, and resubmits the
prompt's token ids followed by the ids of every committed token, asking only
for the remaining budget. Nothing is re-tokenized. This is the recompute
strategy of Section~\ref{sec:model}, done once, on the server side.
(4) \emph{Client reconnect}: a client that lost its connection asks for the
request's stream from a given position and receives exactly the entries it
has not seen. (5) \emph{Gateway restart}: on start, the gateway resumes every
logged request that has no completion record.

\paragraph{What it guarantees, and under which assumptions.} The failure
model is fail-stop crashes of engine and gateway processes; the log directory
survives; and a client that loses its connection remembers the position
after the last entry it consumed. Under these assumptions:
\begin{itemize}
  \item Each output position is committed to the log exactly once and in
    order, and a client that reconnects from its own last consumed position
    receives every remaining position exactly once, in order, unless the
    request fails for good. The gateway does not know what a client received,
    only what it committed: an entry written and sent but lost in transit is
    sent again only because the client asks from its own position. The
    guarantee therefore reaches an application end to end only if the client
    keeps that position durably together with what it consumed; acknowledged
    delivery is not part of the protocol.
  \item \emph{Durability boundary.} An entry is committed when it is written to
    the log file. Without \texttt{--fsync}, as in all kill trials of this paper,
    the write survives a crash of the gateway or engine process, because it is
    already in the operating system's page cache, but not a crash of the
    operating system or a power loss. With \texttt{--fsync}, each entry is
    flushed to the storage device before release (about 3\,ms more before the
    first token on vLLM, Table~\ref{tab:gwoverhead}), which extends the
    guarantee to those failures as far as the device honours the flush. A lost
    disk is outside both.
  \item A \emph{position} is a token with vLLM (ids mode) and a stream chunk
    with SGLang (text mode, below), so the SGLang guarantee is per chunk, and
    its recovery re-tokenizes the delivered text.
  \item The continuation never contradicts delivered text, because the
    delivered tokens are its context. It reproduces the failure-free text only
    where the engine does (Section~\ref{sec:followup}).
  \item In ids mode, the text of the first entries after a failure, and of
    the first entries of a request whose prompt the client sent as token ids,
    is checked against the decoding of the token ids, with the prompt as
    context; text the engine repeated is removed. The text a client
    concatenates then equals what the delivered ids add to the prompt's
    decoding. This was added in version~3, after the engine's text was found
    to repeat delivered text (Section~\ref{sec:live}).
\end{itemize}

\section{Recompute versus a KV copy}
\label{sec:restore}

The gateway recovers by recompute: the replica that takes over rebuilds the KV
cache by prefilling the prompt and the delivered tokens. The proposal behind
this project hypothesised a crossover: recompute wins for short contexts, and
restoring a saved copy of the KV cache wins beyond some length. We measured
both sides.

\paragraph{Recompute.} \texttt{harness/run\_prefill.py} sends prompts of $L$
pseudo-random token ids with \texttt{max\_tokens}=1 and records the time to
the first token, which is the prefill a recompute recovery pays. Every prompt
is distinct, so nothing is served from a cache; five requests per length, one
at a time. Runs with prefix caching on and off agree within 4\,ms at every
length, and the spread over five requests is at most 3\,ms. Prefill took
\RecompMin--\RecompMax\,s from 512 to 32{,}768 tokens, and its rate fell
above 2K tokens as attention's quadratic cost took over. At 32K tokens the
GPU is at its memory limit; one sweep needed vLLM's
\texttt{--gpu-memory-utilization 0.94} to start, which changes the memory
reserved for the cache, not prefill speed.

\paragraph{Copy.} \texttt{harness/kv\_copy\_bench.py} allocates a buffer of
the model's KV size for $L$ tokens ($2\times32$ layers $\times\,8$ KV heads
$\times\,128\times2$ bytes $=$ 128\,KiB per token) and times GPU to pinned
host memory and back, and host to the local disk with \texttt{fsync} and
back, with the page cache dropped before every read.
\texttt{harness/kv\_net\_bench.py} moves the same buffers from one machine's
GPU over TCP into the other's GPU (same availability zone, no placement
group), with one and with four TCP streams. Each network session ran a size
sweep, 15 back-to-back transfers of the 4.3\,GB buffer, and the sweep again,
about 150\,GB in all, so that an exhausted burst allowance would show as a
falling rate. These are raw copies on an otherwise idle GPU: lower bounds on
the cost of a checkpoint, not a checkpoint implementation.

\paragraph{There is no crossover where it matters.} Table~\ref{tab:restore}
gives the answer by restore path. From host memory (about 13.4\,GB/s each
way) a restore was 25--39$\times$ faster than recompute at every length. From
the second machine it was 1.9--3.1$\times$ faster with four streams and
1.05--1.66$\times$ with one. The network rate was flat, 5.0\,Gbit/s with one
stream and 9.9\,Gbit/s with four, in every sustained transfer and both
sweeps; 5\,Gbit/s is the single-flow limit EC2 documents outside a cluster
placement group, so a checkpoint stream over one connection gives up half the
benefit. Only the local disk, read at about 350\,MB/s, shows the hypothesised
crossover, at 32K tokens, the top of the range. The margin grows with

512 tokens a copy from the standby saves 0.07\,s, at 32K about 8.4\,s.

standby when the failure happens, so a real checkpoint has to stream it while
the request decodes. One request adds 128\,KiB per output token, about
4\,MB/s at 33\,ms per token, or about 115\,MB/s for 32 concurrent requests,
under 10\% of the four-stream link; but whether streaming at that rate slows
decoding cannot be measured with raw copies on an idle GPU.

\section{Checkpoint policy: a simulation}
\label{sec:sim}

\textbf{This section reports a simulation, not a measurement.} The original
plan for the last research question was an adaptive policy that decides per
request whether to checkpoint, recomputing short requests and checkpointing
long ones. Section~\ref{sec:restore} removed the premise: restoring from the
standby wins at every length. What remained open was how often to stream new
KV entries, given an unknown cost on the decode path. Before building a live
system we simulated the question with a model whose hardware costs are read
from the committed logs of the measurements above, and wrote down, before
running it, the rule that would decide whether the live system was worth
building (\texttt{docs/phase5-plan.md}).

\paragraph{Model.} Inputs read from logs: the recompute cost $R(n)$ and copy
rates of Section~\ref{sec:restore}, the four-stream network rate, 33.1\,ms
per output token from Section~\ref{sec:load}, and \SimDetect\,s of failover
detection and switching from Section~\ref{sec:gweval} (the failover recovery
there, minus the prefill it includes; version~3 reran the simulation with
this input taken from the gateway's log instead of the client, which lowered
it from 0.125\,s and lowered every simulated recovery time by about 0.09\,s,
without changing any decision). Assumptions, swept or
stated: the share $\beta\in\{0,0.1,0.5,1\}$ of a checkpoint's copy time that
stalls decoding; a mean time between replica failures of 1~day, 1~hour or
10~minutes, fail-stop and Poisson, with a first-order expected cost (at most
one failure per request; the largest failure rate times request duration in
the grid is 0.13); three workloads of 2{,}000 requests each, \emph{chat}
(prompts of 64--2{,}048 tokens, outputs of 64--512), \emph{long} (prompts of
4{,}096--28{,}000 tokens, outputs of 256--2{,}048) and \emph{mixed} (80\%
chat, 20\% long); one request at a time; a standby always available.
Policies decide at the end of prefill and every 16 output tokens:
\emph{recompute} (the gateway as built), \emph{prompt-only} (checkpoint the
prompt's KV once), \emph{fixed-$k$} (after prefill and every $k$ tokens,
$k\in\{16,64,256,1024\}$), and two adaptive rules, the proposal's inequality
and one weighing the remaining time of the request against the saving per
failure.

\paragraph{Decision rule.} For each configuration the baseline is the best
non-adaptive policy by expected completion time, chosen in hindsight. An
adaptive policy wins if it lowers expected completion time by at least 5\%,
or 99th-percentile recovery latency by at least 5\% while being at most
0.1\% slower in expectation. A live adaptive policy would be built only if one
won on the mixed workload for $\beta\in\{0.1,0.5\}$ at a failure rate of one
hour or rarer.

\paragraph{Result: no adaptive policy.} Neither adaptive rule won a single
configuration, in any workload. At a failure every hour, a
\SimMixedT\,s mixed request fails with probability of about 0.4\%, so even
removing all recovery time saves at most a few milliseconds per request on
average, while a checkpoint that stalls decoding for a tenth of its copy time
already costs \SimOvhMin--\SimOvhMax\% in this workload. Both adaptive rules work this out and stop
checkpointing as soon as checkpoints cost anything ($\beta\geq0.1$ at failure
rates of an hour or rarer), so they match the best non-adaptive policy, which
is then recompute, and cannot beat it (Table~\ref{tab:sim}). Adaptivity buys
nothing measurable in expected completion time, for the modeled workloads,
policies and failure rates; we do not claim it for others.

\paragraph{What checkpointing buys is tail latency.} For failures during
decoding, every checkpointing policy cuts recovery sharply: p99 from
\SimPninetynineRecompute\,s under recompute to \SimPninetyninePrompt\,s with prompt-only and
\SimPninetynineFixed\,s with a checkpoint every 16 tokens. Prompt-only captures most of the gain for one
copy per request. A failure during prefill (\SimPrefillShare\% of failure
positions in the mixed workload) is still recovered by redoing the prefill
under every policy. The simulation thus narrowed the live work to measuring
the decode-path cost of a fixed policy and the recovery it buys.

\section{A KV checkpoint inside vLLM}
\label{sec:live}

vLLM~0.31 can offload KV-cache blocks from the GPU to other storage through
its \texttt{OffloadingConnector}. We used it unmodified as a checkpoint: both
replicas write blocks to, and look blocks up in, one directory that the
standby can read, and the gateway resumes a failed request on the standby as
before. If the blocks for the prompt and the delivered tokens are there, the
standby loads them instead of recomputing them.

\paragraph{Setup.} Two \texttt{g5.xlarge} machines in one availability zone,
vLLM~0.31.0, Llama~3.1~8B~Instruct, a 17{,}000-token context cap, greedy
decoding, 256 output tokens. The first machine runs the gateway and replica~0;
the second runs the standby and exports a 6\,GB RAM disk over NFS
(\texttt{nconnect=4}), mounted on both at the same path. Each replica's
connector keeps a 4\,GiB CPU tier backed by a second tier in that directory;
block hashes use the same seed in both processes, so a block written by one is
found by the other. Three modes: \emph{none}, no connector, so the standby
recomputes as in Section~\ref{sec:gweval}; \emph{prompt}, offloading the
prompt's blocks only (vLLM's default); and \emph{all}, every full 16-token
block, prompt and output. Prompts are pseudo-random token ids, distinct in
every request; the shared directory is emptied before every failover trial,
and vLLM's leftover shared-memory file before every engine start.

\paragraph{Cost while serving.} Replica~0 alone served requests with
4{,}096-token prompts, one and four at a time, two repetitions per mode in
interleaved order (commit \texttt{d9dd746}; Table~\ref{tab:pfbovh}). Time per
output token was unchanged within 0.1\% at one request at a time, and
throughput was within 0.6\% at four. In the simulation's terms, the decode
stall $\beta$ was close to 0, below the whole range simulated, because vLLM
copies blocks off the GPU asynchronously. The cost moved to the first token:
with \emph{prompt} it arrived about 55\,ms (5\%) later, in both repetitions;
with \emph{all} the two repetitions differed (+36 and +3\,ms), for reasons we
did not establish. The 6\,GB RAM disk filled during the $C{=}4$ batches (each
prompt is 537\,MB of KV), after which new blocks could not be written to the
shared tier, so the $C{=}4$ figures cover only part of the copying.

\paragraph{Two sets of runs.} The failover runs were done twice. The first set,
a week before the second, used the gateway as evaluated in
Section~\ref{sec:gweval}, with one fix (the event encoding, below); it showed
that the text a client concatenates could repeat earlier text, which the
gateway then learned to remove. The second set (commit \texttt{1b978f2},
Tables~\ref{tab:pfbfo} and~\ref{tab:pfbcc}) repeated the single-request
trials with that fix, added a check of the client's text, and added failures
with 4, 16 and 32 requests in flight; its first two attempts were discarded,
one because the gateway lost requests (below) and one because two copies of
the experiment ran on the same machines at once. Recovery figures of the
first set, taken from the gateway's log, agree with the second within
0.05\,s.

\paragraph{Recovery, one request at a time.} Replica~0 was SIGKILLed once 128
output positions had reached the client, with prompts of 4{,}096 and
16{,}384 tokens (Table~\ref{tab:pfbfo}). All \PfbTrials{} trials delivered
every position exactly once, and in all \PfbTextOk{} the client's text was
right. With a checkpoint the standby resumed in
\PfbSixteenPrompt--\PfbSixteenAll\,s instead of \PfbSixteenNone\,s at 16K
tokens, and in \PfbFourPrompt\,s instead of \PfbFourNone\,s at 4K. The
standby demonstrably used the checkpoint: its loaded bytes rose by 537\,MB at
4K and 2{,}147\,MB at 16K with \emph{prompt}, exactly the prompt's KV at
128\,KiB per token, and slightly more with \emph{all}, which also stores the
decoded blocks; in the first set, its log reported an external prefix-cache
hit rate of 98.8--99.8\%. \emph{All} was no faster than \emph{prompt}, since
only 128 decoded tokens were at stake. We did not break the remaining
0.2--0.6\,s down; it includes loading up to 2\,GB over NFS and recomputing
what was not stored. In both checkpoint modes, and in both sets of runs,
the first 4K trial took 0.56--0.60\,s, against 0.20--0.24\,s for almost all
the others, consistent with a first-use cost on the freshly started standby
(the first set also had one later slow trial, and a slow first trial without
a checkpoint).

\paragraph{Recovery with many requests in flight.} With $C$ requests running
when replica~0 died, every request was resumed on the standby
(Table~\ref{tab:pfbcc}): all \PccRecords{} requests received every position
exactly once. Without a checkpoint the standby must recompute all $C$
requests at once, about 37{,}000 tokens of prompt and delivered output at
$C{=}32$, so requests queue: median recovery rose from \PccFourNone\,s at
$C{=}4$ to \PccSixteenNone\,s at 16 and \PccThirtyTwoNone\,s at 32, with the
slowest request at \PccThirtyTwoNoneMax\,s. With \emph{prompt} the standby
loaded the prompts instead (537\,MB at $C{=}4$, about 4.8\,GB at 32), and
median recovery was \PccFourPrompt, \PccSixteenPrompt{} and
\PccThirtyTwoPrompt\,s, the slowest \PccThirtyTwoPromptMax\,s; with
\emph{all} at $C{=}16$ it was \PccSixteenAll\,s. The checkpoint's benefit
therefore grows with the number of requests a failure interrupts, not only
with their length. These results hold for the conditions tested: one prompt
length (1{,}024 random token ids), vLLM's default mode, one kill per trial
timed on one request, three trials per cell and one pair of machines; they
do not establish behaviour under arbitrary workloads. Time to first token in this table includes queueing on
replica~0, which served all $C$ requests at once.

\paragraph{The checkpoint is paid for on every request.} Time to first token
on replica~0 rose from \PfbFourNoneTtft{} to \PfbFourPromptTtft\,s at 4K
(8\%) and from \PfbSixteenNoneTtft{} to \PfbSixteenPromptTtft\,s at 16K (5\%),
consistent with the 5\% of the serving-cost runs. At 16K a failure saves about
4.5\,s and every request pays about 0.3\,s, so in expected completion time the
checkpoint pays off only if more than about one request in 15 meets a failure.
The measured cost thus lands on the prefill, which the simulation did not
model, rather than on decoding, which it did. The live measurements therefore
support the simulation's qualitative conclusion, that checkpointing buys tail
recovery latency rather than average speed, but they do not validate its
quantitative predictions: its overhead column assumed a decode stall, and the
first-token cost actually measured is outside its model.

\paragraph{Positions were exactly-once; the text, at first, was not.} In the
first set of runs, in \PfbEcho{} of \PfbOldTrials{} trials, the first entry
after the resume carried as its text 24{,}000--97{,}000 characters: the whole
decoded prompt, then the text already delivered, then the new token's text.
The token ids were correct and every position arrived once, but a client that
concatenates the text, as streaming clients do, would have displayed the
prompt and repeated what it had already shown: duplication at the level a
user sees. The 9 cases were exactly the trials in which the last delivered
token streamed with empty text, as a token holding only part of a UTF-8
character does (the random-token prompts make the model emit such tokens),
and none of the other 21; so a resume whose token-id prompt ends inside a
character made vLLM's streamed text start from the beginning of the sequence.
We did not trace this inside vLLM. None of the 190 trials of
Section~\ref{sec:gweval}, with natural-language text, showed it, but a kill
inside a multi-byte character (an emoji, CJK text) could. The gateway now
checks the first entries after a resume against the decoding of the token ids
(\texttt{/detokenize} of prompt plus delivered plus new ids, minus that of
prompt plus delivered ids), holds back a token whose decoding ends in an
incomplete character, removes text the engine repeated, and otherwise keeps
the engine's text, which omits special tokens that \texttt{/detokenize}
shows. In the second set the engine repeated earlier text after a resume
\RevRepeatRemoved{} times in \RevRecords{} requests, and the gateway removed it
every time. The client's text was right in \RevTextOk{} of \RevRecords{}
requests (\texttt{analysis/recheck\_text.py}, with the model's tokenizer). The
3 exceptions, at $C{=}32$, involved no failure: each was a request whose
token-id prompt ended inside a character that the first output token
completed. vLLM repeated the prompt as that token's text, and the gateway,
which then decoded the output ids without the prompt, did not recognise the
repetition and passed it on. Decoding with the prompt as context fixes this
(commit \texttt{852962e}, with a test against a mock engine that imitates
it). A text prompt, which the gateway tokenizes itself, ends on a whole
character and cannot trigger the case.

\paragraph{A targeted check of the fix.} Because the case is rare in random
prompts, we then provoked it on purpose (\texttt{harness/run\_text\_boundary.py},
commit \texttt{4e2441c}, one machine, no failures): eight texts with
multi-byte characters (Chinese, Japanese, Korean, accented Latin, emoji,
Cyrillic, Devanagari, Arabic) were tokenized by vLLM and cut wherever the
token prefix decoded to an unfinished character. That gave only \TbPrompts{}
prompts, because Llama~3 encodes most of these characters as whole tokens.
Each was sent, 32 output tokens, through the fixed gateway and, as a control,
through a gateway that releases the engine's text, once with one request in
flight and once with 16. With the control, the client's text was right in
\TbEngineOneOk{} of \TbPrompts{} at both levels: vLLM repeated the prompt in
the others. With the fix, it was right in \TbDeriveOneOk{} of \TbPrompts{}
with one request and \TbDeriveSixteenOk{} of \TbPrompts{} with 16, the gateway
having removed the repetition in \TbDeriveOneRemoved{} and
\TbDeriveSixteenRemoved{} of them; every position was exactly once in all 44
requests. Text was checked with the model's tokenizer, decoding the output
with the prompt as context and leaving out special tokens by id. The 387 of
390 above stays as measured; this check shows the fix works on the case that
caused its 3 exceptions, on a small sample.

\paragraph{Problems found by the concurrent runs.} Three faults in our own
code surfaced only with many requests in flight; all are fixed. The gateway's HTTP server kept Python's default
backlog of five pending connections, so when 32 clients connected at once,
three connections were reset and those requests never started; the backlog
is now 1{,}024, and the client chooses the request id, so that a submission
whose connection failed is resumed if the gateway started it and submitted
again if not. The client delay described in Section~\ref{sec:gweval} was
found while checking the kill timing of these runs. And the reader that
replaced \texttt{iter\_lines} did not translate the error raised when a
killed engine's chunked stream is cut, so requests ended at the kill instead
of failing over; this was caught in the first trials and fixed before the
runs reported here.

\paragraph{An event-stream bug.} In the first set of runs, one interrupted run
had a repeated text containing the character U+0085. The gateway sent its
event stream without a charset, so the Python \texttt{requests} library
decoded it as Latin-1, and splitting the decoded text into lines treated
U+0085 as a line break, cutting one event in two; the client's checker
reported a missing position. The gateway now escapes every non-ASCII
character in its JSON events, declares UTF-8, and its client splits lines as
bytes (commit \texttt{c1b065e}). The 190 trials of Section~\ref{sec:gweval}
ran on the earlier code; none of them hit any of the problems in this
section.

\section{Discussion}

\paragraph{Two engines, two mechanisms, one consequence.} vLLM's variation
was deterministic and tied to its prefix cache; SGLang's was tied to server
start and was not repeatable across starts. A client cannot tell these
apart, and for a client they have the same effect: the server that answers
a retry is freshly started, and a freshly started server did not reproduce
the text the client had been shown, in 25 of 30 vLLM and 24 of 30 SGLang
trials.

\paragraph{Retry is not replay.} The usual argument for retrying an LLM
request is that at temperature 0 it is idempotent up to duplication. On the
default vLLM configuration measured here, it was not: the server that
answers a retry is a fresh process, and a fresh process gave a different
greedy answer from the warm one that had been streaming. For a chat client
this means a visible rewrite of text already shown in most trials on both
engines; for an
agent that acted on a partial tool call or plan, it means the action was
based on text that the final answer contradicts.

\paragraph{What a client and an operator should do.} With default
engine settings, recompute is the only client-side strategy that never
contradicted what was shown, at the
price of a final answer that no failure-free run produced, and a few tens of
milliseconds of extra prefill. Naive retry with deduplication is unsafe
unless the client verifies that the replay begins with $D$, and should
replace rather than splice when it does not. On vLLM, disabling automatic
prefix caching removed the contradictions for sequential requests, but under
concurrent load it no longer made the output unique
(Section~\ref{sec:load}), so it is not a fix for a busy server. On SGLang,
disabling the radix cache did not help even sequentially. The combination
that worked on both engines
was an engine deterministic mode on the server and recompute on the client:
at temperature 0 it reproduced the failure-free output exactly in all 35
trials (Section~\ref{sec:followup}), without any change to the engines'
code. The client ended with the same text as a failure-free run, the
outcome exactly-once delivery would guarantee. That is equivalence in the
tested configurations, not an exactly-once protocol: it relied on greedy
decoding and the operator enabling the mode, and it costs about half the
throughput (Section~\ref{sec:load}). Under load the modes still gave one
output per prompt, but recovery was not injected under load.

\paragraph{What the gateway changes.} Client-side recovery could not
remove contradictions without the operator enabling a deterministic mode,
and left every client to implement recompute and deduplication correctly.
The gateway makes exactly-once delivery a property of the serving layer:
every position once, in order, for unmodified engines and for ordinary
streaming clients when an engine fails, in every trial we ran, including with
32 requests in flight, at a per-token cost below 1\%. (A client that must
survive losing its own connection additionally keeps its position and
reconnects from it.) What it cannot add is
determinism. Whether the recovered text equals a failure-free run is still
decided by the engine: its deterministic mode, its sampler, and, after
failover, whether the standby matches the failed replica's compiled state,
which in our runs it did only when the caches were copied.
Version~1 of this paper argued that exactly-once recovery above temperature
0 would also need the sampler's state. On vLLM~0.31 with a fixed request seed
it needs no engine change, because the sampler derives each draw from the
seed and the position; on SGLang, whose default mode ignored the seed, it was
not available.

\paragraph{What a checkpoint adds.} Recovery time fell in three steps across
this study: from minutes, when a crashed engine had to restart, to
\GwFailoverMin--\GwFailoverMax\,s with a standby for a short prompt, and, with
a KV checkpoint on the standby, to under a second for long prompts as well
(\PfbSixteenPrompt\,s instead of \PfbSixteenNone\,s at 16K tokens), and to
\PccThirtyTwoPrompt\,s instead of \PccThirtyTwoNone\,s (median) when 32
requests fail together. The checkpoint needed no engine change, only vLLM's
offloading pointed at shared storage, and the gateway delivered every
position exactly once throughout, although the text needed the fixes of
Section~\ref{sec:live}. Its price was not where we expected it: decoding was
not slowed, but every request's first token came 5--8\% later. Measured and simulated
results agree on the economics: at plausible failure rates no checkpoint pays
for itself in average completion time, and a per-request adaptive policy has
nothing to gain. The case for a checkpoint is a target for worst-case
recovery, for long contexts and for agents that wait on a stream; prompt-only
checkpointing captures most of that gain (Figure~\ref{fig:recovery}).

\section{Related work}

\textbf{Fault-tolerant LLM serving.} D\'ej\`aVu \cite{strati2024dejavu}
is the closest work: it streams and replicates KV cache inside a modified
serving system so that generation can resume after a failure, and evaluates
server-side recovery time and throughput. This paper differs in four ways.
It measures what a streaming \emph{client} receives when unmodified engines
fail, and shows that retry contradicts displayed text in two engines; it
defines a delivery guarantee (each output position exactly once, with the
displayed text checked separately) and evaluates a protocol for it in front
of unmodified engines; it compares two engines' behaviour, including
determinism after recovery and its dependence on compiled state; and it
obtains its KV checkpoint from an engine's existing offloading interface,
measuring the trade-off between first-token cost and recovery latency
rather than building a new replication mechanism. SpotServe \cite{miao2024spotserve} migrates in-flight context when
preemptible instances are reclaimed with warning, and Llumnix
\cite{sun2024llumnix} live-migrates requests for load balancing. Both handle
planned moves; this study targets unplanned fail-stop crashes.
\textbf{Serving engines.} Orca \cite{yu2022orca} introduced iteration-level
scheduling, vLLM \cite{kwon2023pagedattention} block-managed KV memory, and
SGLang \cite{zheng2024sglang} prefix sharing via RadixAttention.
\textbf{Delivery semantics.} Chandy and Lamport \cite{chandy1985snapshots}
define consistent snapshots, Elnozahy et al.\ \cite{elnozahy2002survey}
output commit, and Flink \cite{carbone2015lightweight} and Spark Structured
Streaming \cite{armbrust2018structured} build exactly-once sinks on them.
\textbf{Inference nondeterminism.} He et al.\ \cite{he2025nondeterminism}
show that LLM inference at temperature 0 is not reproducible across server
load because kernels are not batch-invariant, and build batch-invariant
kernels. Our observation is the fault-tolerance consequence: requests here
were issued one at a time, yet output still depended on what the server had
served before, so a retry after a crash is not a replay.
\textbf{KV-cache storage and transfer.} CacheGen \cite{liu2024cachegen}
compresses and streams KV caches over the network to avoid recomputing long
contexts, and Mooncake \cite{qin2025mooncake} builds serving around a
disaggregated KV-cache store; both target efficiency in failure-free
serving, which is the machinery our checkpoint borrows for recovery.
\textbf{Checkpoint intervals.} Classic results on optimal checkpoint
intervals \cite{young1974first,daly2006higher} balance checkpoint cost
against expected lost work; our simulation applies the same reasoning per
request and finds that, at plausible failure rates, the balance favours
checkpointing only for tail latency.

\section{Threats to validity}
\label{sec:threats}

\begin{itemize}
  \item \textbf{Trials are not independent samples.} In vLLM, output was
    deterministic given server history, so 5 trials per configuration are
    repeated observations of one or two histories, and counts such as ``25
    of 30'' describe how many configurations and histories were affected,
    not a sampled rate. In SGLang the cold output varied from start to
    start, so its trials do sample that variation, but 5 per configuration
    is too few to estimate rates.
  \item \textbf{Six prompts, one model, one GPU type.} The main grid used
    one prompt; five more were tested only at temperature 0 and the
    128-chunk kill point, and vLLM's batch invariance only on the main
    prompt. Divergence positions are prompt-specific (two of five extra
    prompts showed no vLLM divergence within 256 tokens). Other models and
    tensor-parallel serving may differ.
  \item \textbf{Default configurations, different kernels.} Each engine
    ran with its own defaults on this GPU (vLLM with PyTorch sampling
    because FlashInfer's sampler could not compile on the host image;
    SGLang with FlashInfer attention and sampling inside its container).
    The comparison is between default behaviours, not kernels.
  \item \textbf{SGLang seed.} The harness's OpenAI-style seed had no
    observable effect on SGLang, so its temperature-0.8 results are for
    unseeded sampling and are not comparable to vLLM's seeded runs.
    Its temperature-0 results do not involve sampling.
  \item \textbf{vLLM sampler substitution.} vLLM ran with PyTorch sampling
    instead of FlashInfer's sampler, because of the missing CUDA toolkit. The
    temperature-0 results do not involve random sampling, but the 0.8
    results may differ under FlashInfer.
  \item \textbf{Mechanism.} For vLLM, the ablation shows that the
    dependence on server history requires automatic prefix caching, and
    re-tokenization was ruled out for recompute. For SGLang, neither the
    radix cache nor the server seed was required, and the source of the
    start-to-start variation was not identified. That both engines'
    deterministic modes removed every contradiction and made recompute exact
    at temperature 0 supports, but does not prove, a numerical explanation
    \cite{he2025nondeterminism}; we did not identify which kernel differs.
    The ablations and follow-up runs covered only the 128-chunk kill point.
  \item \textbf{Re-tokenization in recompute.} Recompute sends $D$ as text,
    which the engine re-tokenizes. We checked this directly for vLLM
    (Section~\ref{sec:followup}): re-tokenization matched in all 10 trials
    checked, at the 128-chunk kill on the main prompt. Other prompts or
    kill points could tokenize differently at the boundary.
  \item \textbf{Concurrent failures, narrowly.} Failures with requests in
    flight were injected only in Section~\ref{sec:live}: one prompt length
    (1{,}024 random token ids), 4, 16 and 32 requests, three trials per cell,
    the kill timed on one request, default mode only. Exact text under
    concurrent failure in a deterministic mode was not tested.
  \item \textbf{Times through the gateway.} These come from the gateway's log
    (Section~\ref{sec:gweval}), stamped when an entry is appended, before it
    is written, optionally fsynced and sent; a client on the same machine
    sees it about a millisecond later, plus the \texttt{fsync}. Version~2's
    client-side figures were too long, by up to about one inter-token
    interval, or about 0.1\,s after a failover.
\item \textbf{Fail-stop only; latency includes restart.} \texttt{SIGKILL}
    is a clean crash; GPU hangs and silent corruption are not modeled. With
    a single instance, recovery includes model reload; a warm standby would
    be faster. Restart time also drifted during the grid (see H3).
\item \textbf{Gateway evaluation scope.} One prompt, one model, requests
    one at a time, 10 trials per run; failover only on vLLM and only with the
    kill after 128 positions; one pair of machines. The compiled-cache
    finding rests on three batch-invariant runs on that pair, and which
    cache matters was not isolated. The gateway's own durability was tested
    only by killing its process with the log on local disk; a lost disk, a
    replicated gateway, and a gateway restart under concurrent requests were not tested. Recovery
    times below one second are bounded by health-check polling. Its
    overhead is that of this implementation.
\item \textbf{Generalizability.} Every measurement used one model
    (Llama~3.1~8B~Instruct), one GPU type (A10G, one per machine), one cloud
    and machine image, two engine versions, and, for the gateway and
    checkpoints, one prompt or one synthetic prompt shape. Larger models with
    tensor or pipeline parallelism have more state to lose, longer restarts
    and different kernels; other GPUs differ in memory and copy bandwidth,
    which moves every recompute-versus-copy ratio; and engines change
    quickly, so the specific behaviours found here (the prefix-cache
    dependence, the start-dependent output, the echoed text) may be fixed or
    replaced in later versions. The delivery problem and the gateway's
    protocol do not depend on these details; the numbers do.
\item \textbf{Checkpoint scope.} Section~\ref{sec:restore} measured raw
    copies of contiguous buffers on an idle GPU. Section~\ref{sec:live} used
    one prompt shape (random token ids), one kill position, five trials per
    cell and one pair of machines; its shared store lives in the standby's
    memory and is lost with the standby, it filled up at four concurrent
    requests, and a failure during prefill still forces a full recompute. A
    SIGKILL is detected at once; a hung GPU would add a detection timeout to
    every mode. In the measured runs the gateway's text check recognised
    special tokens by their text (\texttt{<|...|>}), so a model that wrote
    such a string as ordinary text inside the first entry after a resume could
    have lost it; it now recognises them by id (a token that decodes on its
    own to exactly that shape), with a unit test. That version ran on vLLM
    only in the targeted check of Section~\ref{sec:live}, \TbPrompts{} prompts
    of 32 output tokens with no failure injected, which did not exercise
    special tokens or a resume. The simulation of Section~\ref{sec:sim} is a first-order
    model with stated assumptions, and its conclusions are only as good as
    those assumptions.
\end{itemize}

\section{Conclusion and future work}

In the default configurations of both vLLM and SGLang, the failure-free
output for a fixed prompt was not unique at temperature 0, so the restarted
server that answers a retry did not reproduce what the client had been
shown: naive retry contradicted displayed text in most trials on both
engines, and on three (vLLM) and four (SGLang) of five further prompts. The
cause was not re-tokenization; in vLLM it required prefix caching, and in
SGLang it was tied to server start. Each engine's deterministic mode with
recovery by recompute reproduced the failure-free output exactly in every
temperature-0 trial, and under concurrent load these modes kept the output
unique at about half the throughput; disabling vLLM's prefix cache did not.

A gateway that numbers and logs output positions and resumes from the logged
token ids delivered every position exactly once in all \GwKillTrials{}
injected failures on both engines, for ordinary streaming clients (a client
that must survive losing its own connection also keeps its position), at a
per-token cost below 1\%, and in all \PccRecords{} requests
of failures with up to 32 requests in flight; with a standby replica on a
second machine it recovered in under 0.1\,s instead of minutes. After a
resume, vLLM sometimes repeated earlier text; the gateway removes it. Exact text after recovery remained the engine's
property: it held in deterministic mode after restart, and after failover
only once the failed replica's compiled-kernel caches had been copied to the
standby; which artifact matters is not identified.

Restoring a KV copy from the standby was faster than recomputing it at every
length measured, so the question became how often to checkpoint. A
simulation driven by the measurements, judged by a rule fixed in advance,
found no value in an adaptive per-request policy. Measured live, vLLM's own
KV offloading to storage the standby can read cut recovery at 16K tokens by a
factor of eight, and by a factor of three when 32 requests failed together,
with every position delivered exactly once, no measurable decoding cost, and
5--8\% later first tokens: a tool for bounding worst-case recovery, not for
average speed.

Next stages: (1) isolate which compiled artifact makes identical machines
differ, and whether autotuning is the cause; (2) concurrent failures in
deterministic mode, with natural-language prompts and a replicated gateway;
(3) checkpoint a
long prefill in chunks as it is computed, and keep the store somewhere that
survives the standby; (4) other models, GPUs and tensor-parallel serving.
