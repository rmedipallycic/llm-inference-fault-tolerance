# Phase 4 (RQ3): recompute versus KV checkpoint, measured

**Question.** At what context length, if any, does restoring a saved KV cache
beat recomputing it? The proposal's hypothesis ([proposal](proposal.md), RQ3):
*a crossover exists: recompute wins for short contexts, checkpointing wins past
some context length that depends on hardware and failure rate.*

**Short answer on this hardware** (one NVIDIA A10G per g5.xlarge, Llama 3.1 8B
Instruct in bf16, vLLM 0.31.0): it depends on where the copy lives, and the
hypothesis holds for only one of the three places.

| Restore from | vs. recompute, 512 to 32,768 tokens | Crossover |
|---|---|---|
| Host memory (same machine) | 25-39x faster | none: restore wins at every length |
| Local disk (the root EBS volume) | 0.63-0.80x below 32K, 1.00x at 32K | at about 32K, the top of the range |
| Second machine, 4 TCP streams | 1.9-3.1x faster | none: restore wins at every length |
| Second machine, 1 TCP stream | 1.05-1.66x faster | none, but the margin is small below 8K |

These are **raw copy times**: lower bounds on what a real checkpoint costs, not a
checkpoint implementation. Every number below is generated by
[`analysis/phase4.py`](../analysis/phase4.py) from the committed logs; the full
tables are in [`experiments/phase4_summary.md`](../experiments/phase4_summary.md).

## Recompute cost R(L)

[`harness/run_prefill.py`](../harness/run_prefill.py) sends prompts of L
pseudo-random token ids with `max_tokens=1` and records the time to the first
token, which is the prefill a recompute recovery pays (Phase 1 client-side
recompute and the Phase 3 gateway both resubmit prompt plus delivered tokens).
Every prompt is distinct, so nothing can be served from a cache. 5 requests per
length, one at a time, after one unrecorded warm-up per length.

| L (tokens) | 512 | 1K | 2K | 4K | 8K | 16K | 32K |
|---|---|---|---|---|---|---|---|
| Prefill, median s | 0.137 | 0.270 | 0.496 | 1.027 | 2.206 | 5.028 | 12.542 |
| Tokens/s | 3,735 | 3,798 | 4,129 | 3,989 | 3,714 | 3,259 | 2,613 |

(Prefix caching off, run `20261023T013003Z`; the run with it on, `20261023T010323Z`,
agrees within 4 ms at every length.) Throughput falls above 2K tokens because
attention's cost grows with the square of the context. The spread over 5
requests is at most 3 ms.

**Measurement notes.**
* With one output token, the single token sometimes decodes to empty text (part
  of a multi-byte character) and no text chunk is streamed; for those 10 of 35
  requests per run the request's end time is used, which the "no text" column of
  the summary counts. Their end times equal the other requests' first-token
  times to the millisecond.
* **32K is at this GPU's memory limit.** A 33,000-token context needs about
  4.03 GiB of KV cache. The first prefix-caching-off start found 3.64 GiB free
  after the weights (15.0 GiB) and CUDA graphs and refused to start; the
  caching-on start two minutes later, with identical settings, found 4.43 GiB.
  The caching-off sweep was rerun with `--gpu-memory-utilization 0.94`
  (vLLM's own suggestion to keep the earlier effective size), which changes the
  memory reserved for the cache, not prefill speed. The failed start is in the
  commit message of `995f9e6`; its log was not committed.

## Checkpoint cost on one machine

[`harness/kv_copy_bench.py`](../harness/kv_copy_bench.py) allocates a buffer of
the model's KV size for L tokens (2 x 32 layers x 8 KV heads x 128 x 2 bytes =
**128 KiB per token**, from the model's `config.json`) and times GPU to pinned
host memory, back, and host to local disk with `fsync` and back (page cache
dropped before every read). 5 repetitions per length, GPU otherwise idle.

| L | MB | GPU->host s | host->GPU s | disk write s | disk read s |
|---|---|---|---|---|---|
| 512 | 67 | 0.005 | 0.005 | 0.07 | 0.19 |
| 2,048 | 268 | 0.020 | 0.020 | 0.30 | 0.76 |
| 8,192 | 1,074 | 0.081 | 0.080 | 1.80 | 3.07 |
| 32,768 | 4,295 | 0.320 | 0.319 | 9.06 | 12.24 |

Host memory moves at about 13.4 GB/s each way; the disk reads at about 350 MB/s,
which is why restoring from it never beats prefill below 32K. A copy in host
memory survives only the engine process failing; it is lost with the machine.

## Checkpoint cost to a second machine

[`harness/kv_net_bench.py`](../harness/kv_net_bench.py) moves the same buffers
from one machine's GPU over TCP into the other machine's GPU (sender
`ip-172-31-5-141`, receiver `ip-172-31-6-222`, same availability zone, no
placement group) and times each stage. Each session ran three parts back to
back: the size sweep (5 repetitions each), 15 transfers of the 4.3 GB buffer,
and the size sweep again, about 150 GB in all, so that a burst allowance running
out would show as a falling rate.

| L | MB | 1 stream: total s | ratio | 4 streams: total s | ratio |
|---|---|---|---|---|---|
| 512 | 67 | 0.118 | 1.16 | 0.064 | 2.14 |
| 2,048 | 268 | 0.473 | 1.05 | 0.257 | 1.93 |
| 8,192 | 1,074 | 1.891 | 1.17 | 1.026 | 2.15 |
| 16,384 | 2,147 | 3.783 | 1.33 | 2.052 | 2.45 |
| 32,768 | 4,295 | 7.566 | 1.66 | 4.105 | 3.06 |

Total = sender GPU->host + network + receiver host->GPU, the time until the
standby holds the KV cache on its GPU; ratio = recompute time / total.

* **The rate was flat.** One TCP stream ran at **5.0 Gbit/s** and four at
  **9.9 Gbit/s** in every one of the 15 sustained transfers and in both size
  sweeps; the two sweeps agree to the millisecond. No burst allowance ran out
  within about 150 GB per session. That is the scope of the claim: it does not
  show the rate holds indefinitely.
* **One connection gets half the link.** 5 Gbit/s is the single-flow limit EC2
  documents for traffic outside a cluster placement group, so a checkpoint
  stream over one TCP connection gives up half of the benefit.
* **The margin grows with context**, because prefill grows faster than linearly
  and the copy grows linearly.

## What this means, and what it does not show

* **RQ3's hypothesis is refuted for the restore paths that matter for
  failover.** There is no short-context region where recompute wins against a
  copy in host memory or on the standby (4 streams); the restore is faster at
  every measured length. Only local disk shows the hypothesised crossover, at the
  top of the range.
* **At short contexts the difference is small in absolute terms.** At 512 tokens
  the copy saves 0.07 s over a 0.14 s prefill; Phase 3's whole failover took
  0.16-0.17 s. The case for a checkpoint is long contexts: at 32K it would save
  8.4 s per recovery on the standby.
* **A restore needs the KV cache to be on the standby when the failure
  happens**, so a real checkpoint has to stream it while decoding. Arithmetic
  from the measured link, not a measurement: one request adds 128 KiB per
  output token, about 4 MB/s at Phase 2's 33 ms per token, or about 115 MB/s for
  32 concurrent requests at their 37 ms per token, under 10% of the 4-stream
  link. Whether streaming at
  that rate slows decoding is what a real engine integration would have to
  measure (checkpoint overhead on failure-free requests, a metric in the
  proposal).
* **Not tested:** a real checkpoint through the engine (for example a KV
  offloading connector), non-contiguous KV blocks, concurrent requests, other
  models or GPUs, placement groups, and network rates beyond about two minutes
  of sustained transfer per session.

## Reproduce

```bash
bash scripts/run_phase4.sh                           # prefill sweeps + one-machine copy (one GPU)
python -m harness.kv_net_bench receive --port 8000   # on the standby
bash scripts/run_phase4_net.sh <standby private IP>  # on the first machine
python analysis/phase4.py --out experiments/phase4_summary.md
```
