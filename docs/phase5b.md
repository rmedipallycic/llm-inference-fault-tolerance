# Phase 5 (RQ4), Option B: a KV checkpoint inside vLLM (measured)

**Measured, not simulated.** Option A ([phase5-simulation.md](phase5-simulation.md))
ruled out an adaptive policy and narrowed Option B to two questions: what does
streaming the KV cache to a standby cost on the decode path, and how much does
it shorten recovery after a replica dies? Every number below comes from the raw
logs in `experiments/` and is regenerated by
`python analysis/phase5b.py --out experiments/phase5b_summary.md`
(full tables: [`experiments/phase5b_summary.md`](../experiments/phase5b_summary.md)).

## Setup

* Two AWS g5.xlarge machines (one A10G each, us-east-2a), vLLM 0.31.0,
  Llama 3.1 8B Instruct, `max_model_len` 17000, greedy decoding, 256 output tokens.
* **Machine 1** runs the Phase 3 gateway (ids mode) and replica 0. **Machine 2**
  runs the standby (replica 1) and exports a 6 GB RAM disk over NFS
  (`nconnect=4`), mounted on both machines at `/srv/kv`.
* Both replicas run vLLM's own `OffloadingConnector` (no changes to vLLM): a
  4 GiB CPU tier backed by a second tier on the shared directory. Block hashes
  are seeded identically, so a block written by replica 0 is found by the standby.
* Three modes:
  * `none`: no connector, the standby recomputes (the Phase 3 behaviour);
  * `prompt`: `offload_prompt_only` (vLLM's default), the prompt's KV only;
  * `all`: every full 16-token block, prompt and decoded tokens.
* Prompts are pseudo-random token ids, distinct in every request, so no request
  can reuse another's blocks; the shared directory is emptied before every
  failover trial and vLLM's leftover shared-memory file before every start.
* Scripts: `scripts/phase5b_*.sh`, `scripts/run_phase5b_overhead.sh`,
  `scripts/run_phase5b_failover.sh`; harness: `harness/run_throughput.py`
  (`--random-prompt-len`) and `harness/run_ckpt_failover.py`.

## 1. Cost of the checkpoint while serving

4096-token prompts, two repetitions per mode in interleaved order
(none, prompt, all, none, prompt, all), on replica 0 alone. Code: commit d9dd746.

| Mode | C=1 TTFT, ms | C=1 TPOT vs none | C=1 tok/s vs none | C=4 TPOT vs none | C=4 tok/s vs none |
|---|---|---|---|---|---|
| none | 1028-1029 | 1.000x | 1.000x | 1.000x | 1.000x |
| prompt | 1082-1086 | 0.999x | 0.995-0.996x | 0.977x | 0.994-0.995x |
| all | 1032-1065 | 0.999x | 0.999-1.001x | 0.998-0.999x | 0.997x |

* **Decoding is essentially unaffected.** Time per output token is the same
  within 0.1% at one request at a time, and throughput is within 0.6% at four.
  In Option A's terms the decode-path stall beta is near 0, below the 0.1-1
  range the simulation assumed, because vLLM copies blocks off the GPU
  asynchronously.
* **The cost moves to time to first token.** With `prompt`, the first token
  arrives 5% later (about 55 ms at 4K tokens), in both repetitions. With `all`
  the two repetitions differ (+36 ms and +3 ms); we do not know why.
* **Caveat at C=4.** The 6 GB RAM disk filled during the C=4 batches (each 4K
  prompt is 537 MB of KV), after which new blocks could not be written to the
  shared tier. The C=4 figures therefore cover only part of the copying and
  are a lower bound on its cost; a larger or evicting store is needed to
  measure sustained load.

## 2. Failover to the standby

Replica 0 was SIGKILLed once 128 output positions had reached the client; the
gateway resumed on the standby with the prompt plus the 128 delivered token
ids. Five trials per cell. Recovery latency is from the kill to the next
position at the client. Code: commit c1b065e.

| Prompt | Mode | Exactly-once | Recovery s, median (range) | TTFT s, median | KV loaded by standby, MB |
|---|---|---|---|---|---|
| 4096 | none | 5/5 | 1.17 (1.14-1.45) | 1.40 | - |
| 4096 | prompt | 5/5 | 0.27 (0.26-0.60) | 1.53 | 537 |
| 4096 | all | 5/5 | 0.24 (0.23-0.56) | 1.52 | 552 |
| 16384 | none | 5/5 | 5.17 (5.17-5.18) | 5.41 | - |
| 16384 | prompt | 5/5 | 0.74 (0.70-0.75) | 5.74 | 2147 |
| 16384 | all | 5/5 | 0.66 (0.65-0.70) | 5.74 | 2162 |

* **Recovery is 4-8 times faster.** At 16K prompt tokens the standby resumes in
  0.66-0.74 s instead of 5.17 s; at 4K, in 0.24-0.27 s instead of 1.17 s. All
  30 trials delivered every position exactly once.
* **The standby really loaded the checkpoint.** Its `vllm:kv_offload_load_bytes`
  rose by 537 MB (4K) and 2147 MB (16K) with `prompt`, exactly the prompt's KV
  at 128 KiB per token, and slightly more with `all`, which also stores the
  decoded blocks. Its log reports an external prefix-cache hit rate of
  98.8-99.8%. We did not break the remaining 0.2-0.7 s down; it includes
  loading up to 2 GB over NFS and recomputing what was not stored (the
  delivered tokens with `prompt`, the last partial block with both).
* **`all` beats `prompt` only slightly** (0.66 vs 0.74 s at 16K), since only
  128 decoded tokens were at stake. It would matter more for later kills.
* **The checkpoint is paid for on every request.** TTFT on replica 0 rose from
  1.40 to 1.52-1.53 s at 4K (+9%) and from 5.41 to 5.74 s at 16K (+6%), in
  failover trials as in the overhead runs. At 16K a failure saves about 4.4 s
  and every request pays about 0.33 s, so in expected completion time the
  checkpoint only pays off if more than about 1 in 13 requests hits a failure.
  This confirms Option A's conclusion with a measured cost: checkpointing buys
  tail recovery latency, not average speed.
* **The 4K recoveries are bimodal.** Most take 0.23-0.27 s, but four of 15 4K
  trials took 0.56-0.60 s (prompt, all) or 1.45 s (none). In all three modes
  the first trial of the run was a slow one, consistent with a first-use cost
  on the freshly started standby; the second slow `prompt` trial (trial 2) is
  unexplained. The 16K runs, which followed the 4K runs on the same standby,
  show no such spread.

## 3. Two things found along the way

**Positions were exactly-once; the text a client shows was not.** In 9 of
the 30 failover trials (all three modes, both lengths; column "echo" in the
summary), the first entry after the resume carried a text of 24,000-97,000
characters: the decoded prompt, then the text already delivered, then the new
token's text. Token ids and positions were correct, but a client that
concatenates `text` would have shown the prompt and repeated what it had already
displayed. The 9 trials are exactly those in which the last delivered token
streamed with empty text, as a token holding only part of a UTF-8 character does
(the random-token prompts make the model emit such tokens), and none of the
other 21; these were not the slow trials. None of the 190 Phase 3 trials showed
it, but a kill inside a multi-byte character (emoji, CJK) could. We did not
trace the cause inside vLLM.

**Fix (after these runs, not yet run on a GPU).** In ids mode the gateway now
derives the text of resumed entries from token ids: it calls the engine's
`/detokenize` on the delivered ids plus the new ones, releases only the text
beyond what it already released, holds back a token whose decoding ends in an
incomplete character (U+FFFD), and goes back to the engine's text once the two
agree. `--engine-text-after-resume` restores the old behaviour. The mock engine's
`--resume-echo` imitates vLLM's behaviour; `tests/test_gateway.py` checks that a
naive client's concatenated text equals the failure-free text after a failover,
and a negative control with the old behaviour fails that check. This relies on
decoding the output ids alone matching their decoding in context, which holds
for Llama 3's byte-level tokenizer.

**The gateway's event stream could be mis-split by a client.** One of those
long texts (in 2 of the 9) contained U+0085 (NEL). The gateway sent `text/event-stream` with no
charset, so `requests` decoded the stream as Latin-1, and Python's
`str.splitlines` treated the NEL as a line break: one event was split in two and
the client reported a missing position. Commit c1b065e escapes every
non-ASCII character in the JSON (`ensure_ascii=True`), declares
`charset=utf-8`, and makes the client split lines as bytes; two regression
tests fail on the old code and pass on the new. Every failover result above
used the fixed gateway; the interrupted run that exposed the bug is kept out of
the tables (raw logs on the first machine, in `~/failed_runs`). The Phase 3
results (190 of 190) were produced with the earlier gateway code; none of those
trials hit the bug, but the code differs.

## What this does and does not show

* It shows that vLLM's built-in offloading, pointed at a directory a standby can
  read, works as a KV checkpoint with no engine changes: negligible decode
  cost, a 5-9% first-token cost, and recovery an order of magnitude closer to
  instant for long prompts.
* One prompt shape (random ids), one kill position (128), five trials per
  cell, one machine pair. Shared-tier load under sustained concurrency was not
  measured (the RAM disk filled), and a failure **during prefill** still forces
  a full recompute: the prompt's checkpoint exists only once the prefill is done.
* Failure detection is not included: the gateway saw the broken connection at
  once because the process was killed. A hung GPU or a lost machine would add
  the detection timeout to every mode equally.
* The shared directory lives in the standby's RAM. If the standby itself is
  lost, so is the checkpoint; that is a deployment choice, not something these
  runs test.
