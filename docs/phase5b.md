# Phase 5 (RQ4), Option B: a KV checkpoint inside vLLM (measured)

**Measured, not simulated.** Option A ([phase5-simulation.md](phase5-simulation.md))
ruled out an adaptive policy and narrowed Option B to two questions: what does
streaming the KV cache to a standby cost on the decode path, and how much does
it shorten recovery after a replica dies? Every number below comes from the raw
logs in `experiments/` and is regenerated by
`python analysis/phase5b.py --out experiments/phase5b_summary.md`
(full tables: [`experiments/phase5b_summary.md`](../experiments/phase5b_summary.md)).

## Setup

* Two AWS g5.xlarge machines (one A10G each, us-east-2a), vLLM 0.31.0,
  Llama 3.1 8B Instruct, `max_model_len` 17000, greedy decoding, 256 output tokens.
* **Machine 1** runs the Phase 3 gateway (ids mode) and replica 0. **Machine 2**
  runs the standby (replica 1) and exports a 6 GB RAM disk over NFS
  (`nconnect=4`), mounted on both machines at `/srv/kv`.
* Both replicas run vLLM's own `OffloadingConnector` (no changes to vLLM): a
  4 GiB CPU tier backed by a second tier on the shared directory. Block hashes
  are seeded identically, so a block written by replica 0 is found by the standby.
* Three modes:
  * `none`: no connector, the standby recomputes (the Phase 3 behaviour);
  * `prompt`: `offload_prompt_only` (vLLM's default), the prompt's KV only;
  * `all`: every full 16-token block, prompt and decoded tokens.
* Prompts are pseudo-random token ids, distinct in every request, so no request
  can reuse another's blocks; the shared directory is emptied before every
  failover trial and vLLM's leftover shared-memory file before every start.
* Scripts: `scripts/phase5b_*.sh`, `scripts/run_phase5b_overhead.sh`,
  `scripts/run_phase5b_failover.sh`; harness: `harness/run_throughput.py`
  (`--random-prompt-len`) and `harness/run_ckpt_failover.py`.

## 1. Cost of the checkpoint while serving

4096-token prompts, two repetitions per mode in interleaved order
(none, prompt, all, none, prompt, all), on replica 0 alone. Code: commit d9dd746.

| Mode | C=1 TTFT, ms | C=1 TPOT vs none | C=1 tok/s vs none | C=4 TPOT vs none | C=4 tok/s vs none |
|---|---|---|---|---|---|
| none | 1028-1029 | 1.000x | 1.000x | 1.000x | 1.000x |
| prompt | 1082-1086 | 0.999x | 0.995-0.996x | 0.977x | 0.994-0.995x |
| all | 1032-1065 | 0.999x | 0.999-1.001x | 0.998-0.999x | 0.997x |

* **Decoding is essentially unaffected.** Time per output token is the same
  within 0.1% at one request at a time, and throughput is within 0.6% at four.
  In Option A's terms the decode-path stall beta is near 0, below the 0.1-1
  range the simulation assumed, because vLLM copies blocks off the GPU
  asynchronously.
* **The cost moves to time to first token.** With `prompt`, the first token
  arrives 5% later (about 55 ms at 4K tokens), in both repetitions. With `all`
  the two repetitions differ (+36 ms and +3 ms); we do not know why.
* **Caveat at C=4.** The 6 GB RAM disk filled during the C=4 batches (each 4K
  prompt is 537 MB of KV), after which new blocks could not be written to the
  shared tier. The C=4 figures therefore cover only part of the copying and
  are a lower bound on its cost; a larger or evicting store is needed to
  measure sustained load.

## 2. Failover to the standby

Two sets of runs. The **first set** (commit c1b065e, 27-28 October) used the
Phase 3 gateway with the event-stream fix below; it found that the text a client
concatenates could repeat earlier text. The **second set** (commit 1b978f2,
29 October) repeated the single-request trials with the gateway that removes
such text, added a check of the client's text, and added failures with 4, 16
and 32 requests in flight. Tables below are the second set; generated by
`analysis/phase5b.py` (full table: `experiments/phase5b_summary.md`).

**Times through the gateway come from the gateway's log.** Until commit 64c39ec
the measuring client read the gateway's stream with requests' `iter_lines()`,
which waits for 512 bytes on a stream without chunked transfer encoding, so the
client saw each event when the next one arrived. Recovery and first-token times
through the gateway are therefore taken from the gateway log's timestamps
(`analysis/gw_timing.py`), for both sets and for Phase 3. Direct requests to
vLLM (chunked) were not affected.

### One request at a time

Replica 0 was SIGKILLed once 128 output positions had reached the client; the
gateway resumed on the standby with the prompt plus the delivered token ids.
Five trials per cell. "Text ok": the client's concatenated text equals the
model tokenizer's decoding of the delivered ids, special tokens identified by id
(`analysis/recheck_text.py` as of commit 8916c5a, run on the first machine; it
decoded the output ids without the prompt, the version after 852962e decodes
them in context). "Repeats removed":
trials in which vLLM repeated earlier text after the resume and the gateway
removed it.

| Prompt | Mode | Exactly-once | Text ok | Recovery s, median (range) | TTFT s | KV loaded, MB | Repeats removed |
|---|---|---|---|---|---|---|---|
| 4096 | none | 5/5 | 5/5 | 1.08 (1.08-1.12) | 1.40 | - | 1 |
| 4096 | prompt | 5/5 | 5/5 | 0.24 (0.21-0.59) | 1.51 | 537 | 0 |
| 4096 | all | 5/5 | 5/5 | 0.24 (0.21-0.56) | 1.53 | 552 | 0 |
| 16384 | none | 5/5 | 5/5 | 5.14 (5.10-5.14) | 5.41 | - | 0 |
| 16384 | prompt | 5/5 | 5/5 | 0.64 (0.64-0.67) | 5.70 | 2147 | 0 |
| 16384 | all | 5/5 | 5/5 | 0.65 (0.63-0.67) | 5.73 | 2162 | 0 |

* **Recovery is 4-8 times faster** with a checkpoint: 0.64-0.65 s instead of
  5.14 s at 16K, 0.24 s instead of 1.08 s at 4K. The first set agrees within
  0.05 s (from the gateway log; its client-side figures were 0.02-0.06 s longer).
* **The standby really loaded the checkpoint:** `vllm:kv_offload_load_bytes`
  rose by exactly the prompt's KV (128 KiB per token) with `prompt`, slightly
  more with `all`; in the first set the standby's log reported an external
  prefix-cache hit rate of 98.8-99.8%.
* **First-trial effect:** in both checkpoint modes and both sets, the first 4K
  trial took 0.56-0.60 s against 0.20-0.24 s for almost all others.
* **The checkpoint is paid for on every request:** TTFT 1.40 -> 1.51 s at 4K
  (+8%), 5.41 -> 5.70 s at 16K (+5%). At 16K a failure saves about 4.5 s and
  every request pays about 0.3 s: worth it in average time only if more than
  about 1 request in 15 fails. It buys tail recovery latency, not average speed.

### Many requests in flight

C requests at once (1,024 random-token prompts, 256 output tokens), replica 0
killed once request 0 had received 128 positions, 3 trials per cell, one record
per request (`scripts/run_phase5b_concurrent.sh`).

| C | Mode | Requests | Exactly-once | Text ok | Recovery s, median (range) | TTFT s | KV loaded per trial, MB | Repeats removed |
|---|---|---|---|---|---|---|---|---|
| 4 | none | 12 | 12/12 | 12/12 | 0.98 (0.30-1.20) | 0.93 | - | 1 |
| 4 | prompt | 12 | 12/12 | 12/12 | 0.27 (0.12-0.48) | 1.06 | 537 | 1 |
| 16 | none | 48 | 48/48 | 48/48 | 2.73 (0.31-4.48) | 2.72 | - | 7 |
| 16 | prompt | 48 | 48/48 | 48/48 | 0.95 (0.25-1.07) | 2.54 | 2147 | 6 |
| 16 | all | 48 | 48/48 | 48/48 | 0.53 (0.29-0.72) | 2.79 | 2382 | 10 |
| 32 | none | 96 | 96/96 | 95/96 | 4.86 (0.33-15.20) | 4.67 | - | 19 |
| 32 | prompt | 96 | 96/96 | 94/96 | 1.48 (0.42-8.00) | 4.65 | 4817 | 19 |

* **Every request was resumed exactly once**, 360 of 360.
* **Without a checkpoint the standby recomputes all C requests at once**
  (about 37,000 tokens at C=32), so requests queue: median recovery 0.98 s at
  C=4, 2.73 s at 16, 4.86 s at 32, the slowest 15.2 s. With `prompt` it loads
  them instead: 0.27, 0.95 and 1.48 s, the slowest 8.0 s; with `all` at C=16,
  0.53 s. The benefit grows with the number of requests a failure interrupts.
* TTFT here includes queueing on replica 0, which served all C requests.

## 3. The text a client sees

**Repeated text after a resume.** In the first set, in 9 of 30 trials, the
first entry after the resume carried 24,000-97,000 characters: the decoded
prompt, the text already delivered, and the new token's text. Positions were
exactly-once, but a client that concatenates `text` would have shown the prompt
and repeated what it had shown. The 9 trials were exactly those in which the
last delivered token streamed with empty text (part of a UTF-8 character;
random-token prompts make the model emit such tokens). None of the 190 Phase 3
trials showed it; a kill inside a multi-byte character (emoji, CJK) could.

**The fix.** The gateway now checks the first entries after a resume (and the
first entries of a request whose prompt the client sent as token ids) against
`/detokenize` of prompt + delivered + new ids minus prompt + delivered ids. It
holds back a token whose decoding ends in an incomplete character, removes text
the engine repeated, and otherwise keeps the engine's text (which, unlike
`/detokenize`, omits special tokens). `--engine-text-after-resume` restores the
old behaviour.

**Validated on vLLM (second set).** The engine repeated earlier text after a
resume 64 times in 390 requests; the gateway removed it every time. The client's
text was right in 387 of 390. The 3 exceptions (C=32) involved no failure: a
token-id prompt ending inside a character that the first output token
completed; vLLM repeated the prompt, and the gateway, which then decoded the
output ids without the prompt, did not recognise it. Decoding with the prompt
as context fixes this (commit 852962e; checked on vLLM below). Text prompts, tokenized by the gateway, end on a whole character
and cannot trigger it.

**Targeted check of that fix (29 October, commit 4e2441c, one machine, no
failures).** `scripts/run_text_boundary.sh` cuts eight multi-byte texts (CJK,
emoji, accented Latin, Cyrillic, Devanagari, Arabic) wherever the token prefix
decodes to an unfinished character: 11 prompts (Llama 3 encodes most such
characters as whole tokens). Each goes through the fixed gateway and, as a
control, a gateway that releases the engine's text, with 1 and with 16
requests in flight; text checked with the tokenizer (`analysis/recheck_text.py`).

| Gateway | 1 in flight | 16 in flight |
|---|---|---|
| with the text check | 11/11 text right (repetition removed in 10) | 11/11 (removed in 10) |
| control (engine text) | 1/11 | 1/11 |

Every position was exactly once in all 44 requests. The 387/390 of the rerun
stays as measured; this shows the fix on the case behind its 3 exceptions, on
a small sample. Runs: `experiments/20261029T212043Z_textboundary_*`.

**The harness's own text check** first removed anything shaped like `<|...|>`
from the decoding; that misfired when the model wrote
`<|reserved_special_token_173|>` as ordinary text. `analysis/recheck_text.py`
identifies special tokens by id instead; the "text ok" columns use it.

## 4. Problems found along the way, all fixed

* **Event stream mis-split (first set).** The gateway sent `text/event-stream`
  without a charset; `requests` decoded it as Latin-1 and `str.splitlines`
  split a JSON event on U+0085. Fixed in c1b065e (ASCII-only JSON, UTF-8
  declared, client splits bytes).
* **Lost submissions (an aborted attempt of the second set).** The gateway's
  HTTP server had Python's default backlog of 5; with 32 clients connecting at
  once, 3 connections were reset and those requests never started. Backlog now
  1,024; the client chooses the request id, so a failed submission is resumed or
  resubmitted (64c39ec).
* **The client saw events late** (see section 2; 64c39ec).
* **A cut chunked stream ended the request** instead of failing over, after the
  client switched to `read1`: urllib3's own exception was not translated.
  Caught in the first trials, fixed in 1b978f2 before the runs reported here.
* **Discarded attempts** of the second set: the one with lost submissions, and
  one in which two copies of the experiment ran on the same machines at once.
  Their logs are not part of the results.

## What this does and does not show

* vLLM's built-in offloading, pointed at a directory a standby can read, works
  as a KV checkpoint with no engine changes: negligible decode cost, a 5-8%
  first-token cost, and recovery up to an order of magnitude faster, more so
  when many requests fail together.
* One prompt shape (random ids), one kill position (128), 3-5 trials per cell,
  one machine pair, default mode only. A failure **during prefill** still forces
  a full recompute. The shared store lives in the standby's RAM and is lost with
  the standby. Failure detection is immediate for a killed process; a hung GPU
  would add a timeout to every mode.
